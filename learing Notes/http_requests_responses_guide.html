Level One

Absolute Fundamentals

1. What Is HTTP?

HTTP (HyperText Transfer Protocol) is the protocol that defines how a client (like a browser or a mobile app) and a server exchange data over the web. It's a set of agreed-upon rules: how a request should be formatted, how a response should look, and what happens in between.

HTTP is stateless — each request is handled independently, with no memory of previous requests by default. That's exactly why concepts like Cookies, Sessions, and Tokens exist later on — to simulate "memory" across otherwise disconnected requests.

.NET parallel: think of HTTP as the equivalent of the wire protocol underneath ASP.NET's request pipeline — the actual "language" that Kestrel and the browser speak to each other, regardless of what framework sits on top.

2. Client vs. Server

ClientServer
RoleInitiates requests (browser, mobile app, Postman, another server)Listens for requests and sends back responses
ExamplesReact app, mobile app, curl commandNode.js/Express app, ASP.NET Core app
Direction"I want something""Here's what you asked for" (or an error)
A single machine can be both — for example, one API server acting as a client when it calls another external API (a payment gateway, for instance).

3. What Is a Request?

A request is what the client sends to the server, asking it to do something — fetch data, create a record, update something, or delete it. Every request has a method, a URL, headers, and (optionally) a body.

GET /products/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...

4. What Is a Response?

A response is what the server sends back after processing the request — a status code, headers, and (usually) a body containing the requested data or an error message.

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 42, "title": "Laptop HP", "price": 15000 }

5. HTTP Methods

MethodPurposeTypical Use
GETRetrieve dataFetch a product, list users
POSTCreate new dataCreate an order, register a user
PUTReplace an entire resourceOverwrite a user's full profile
PATCHPartially update a resourceUpdate just the user's email
DELETERemove a resourceDelete a product
Tip
  • PUT vs. PATCH is a common interview trap: PUT conceptually replaces the whole resource (missing fields could be wiped/reset), while PATCH only touches the fields you send. In practice, many APIs use PUT loosely as "update," so always check the documentation of the API you're consuming.

6. The Request–Response Lifecycle

The full journey of a single HTTP call, end to end:

  1. The client builds a request (method, URL, headers, body).
  2. DNS resolves the domain to an IP address.
  3. A TCP connection is established (and a TLS handshake, if HTTPS).
  4. The request travels to the server.
  5. The server's routing layer matches the URL/method to a handler.
  6. The handler processes the request (queries a database, runs business logic).
  7. The server builds and sends back a response.
  8. The client receives the response and acts on it (renders UI, throws an error, etc.).

URL Details

7. URL Structure Recap

A full URL breaks down into: scheme://host:port/path?query#fragment. In the context of an HTTP request specifically, the "Request URL" is everything the client sends the server to identify exactly which resource is being requested — typically the path plus the query string (the host is used earlier, to establish the connection itself; the fragment never leaves the browser).

https://api.example.com:443/products/42?fields=title,price#top
PartValueSent to Server?
Scheme + Host + Porthttps://api.example.com:443Used to establish the connection
Path/products/42Yes — part of the request line
Query?fields=title,priceYes — part of the request line
Fragment#topNo — browser-only

8. Path Parameters vs. Query Parameters

/users/123            ← Path Parameter
/users?role=admin      ← Query Parameter

Rule of thumb: if the value is a core, essential part of identifying the resource (like a specific user's ID), it's a path parameter. If it's optional, used for filtering/sorting/pagination, it's a query parameter.

// Express.js
app.get("/users/:id", (req, res) => {
  console.log(req.params.id);   // path parameter
});

app.get("/users", (req, res) => {
  console.log(req.query.role);  // query parameter
});

Request & Response Details

9. Request Headers

Headers are metadata sent alongside the request — information about the request itself, not the actual data being requested.

HeaderPurpose
AuthorizationCarries credentials (e.g., a Bearer token)
Content-TypeTells the server the format of the request body (e.g., application/json)
AcceptTells the server what response format the client can handle
User-AgentIdentifies the client software (browser, app version)
CookieSends stored cookies back to the server

10. Request Body

The actual data payload sent with the request — used with POST, PUT, and PATCH, but not typically with GET or DELETE.

POST /users HTTP/1.1
Content-Type: application/json

{ "name": "Ashraf", "email": "ashraf@example.com" }
Note: GET requests technically can have a body per the HTTP spec, but it's widely unsupported/ignored by servers and proxies in practice — never rely on a GET body; use query parameters instead.

11. Response Headers

Metadata about the response itself.

HeaderPurpose
Content-TypeFormat of the response body (e.g., application/json, text/html)
Content-LengthSize of the response body in bytes
Set-CookieInstructs the client to store a cookie
Cache-ControlHow long/whether the response can be cached
Access-Control-Allow-OriginWhich origins are allowed to read this response (CORS)

12. Response Body

The actual data returned — commonly JSON for APIs, HTML for web pages, or binary data for files/images.

{
  "status": "success",
  "data": { "id": 42, "title": "Laptop HP" }
}

13. Content Types (MIME Types)

The Content-Type header tells the receiving side exactly how to interpret the raw bytes of the body.

MIME TypeMeaning
application/jsonJSON data
application/x-www-form-urlencodedStandard HTML form data, URL-encoded
multipart/form-dataForm data including file uploads
text/htmlHTML content
image/png, image/jpegBinary image data
application/pdfPDF binary content

14. HTTP Status Codes

RangeCategoryCommon Examples
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirection301 Moved Permanently, 302 Found, 304 Not Modified
4xxClient Error400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests
5xxServer Error500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable
Tip
  • 401 vs. 403 is a classic interview question: 401 (Unauthorized) means "I don't know who you are" (missing/invalid credentials); 403 (Forbidden) means "I know who you are, but you're not allowed to do this."
  • Return the most specific status code available — resist the urge to always return 200 with an error message buried in the body.

Security & Identity

15. HTTP vs. HTTPS

HTTPS is HTTP layered on top of TLS/SSL encryption. The data exchanged is encrypted in transit, preventing eavesdropping (man-in-the-middle attacks) and verifying the server's identity via a certificate. Functionally, the request/response structure is identical — HTTPS just wraps it in an encrypted tunnel.

16. Cookies

A small piece of data the server asks the browser to store (via the Set-Cookie header), which the browser then automatically sends back on every subsequent request to that domain. Commonly used to maintain login state, track sessions, or store preferences.

Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Strict
FlagPurpose
HttpOnlyJavaScript cannot read the cookie (protects against XSS stealing it)
SecureOnly sent over HTTPS
SameSiteControls whether the cookie is sent on cross-site requests (protects against CSRF)

17. Sessions

Since HTTP is stateless, a "session" is a server-side mechanism to remember a user across multiple requests. Typically, the server stores session data (in memory, Redis, or a database) keyed by a session ID, and gives that ID to the client as a cookie. Each subsequent request includes the cookie, letting the server look up the associated session data.

18. Authentication & Authorization

AuthenticationAuthorization
Question answered"Who are you?""What are you allowed to do?"
ExampleLogging in with email/passwordChecking if this user's role permits deleting a product
Failure status401 Unauthorized403 Forbidden

19. JWT (JSON Web Token)

A compact, self-contained token format used to represent claims (like user ID, role, expiration) that can be verified without a database lookup, since it's cryptographically signed. A JWT has three parts separated by dots: header.payload.signature.

eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOiIxMjMifQ.4f8s9d...
Key idea: the payload is only base64-encoded, not encrypted — anyone can decode and read it. Never store sensitive secrets in a JWT payload; the signature only guarantees the token wasn't tampered with, not that its contents are hidden.

20. Bearer Token

A convention for sending a token (often a JWT) in the Authorization header, telling the server "whoever holds this token is authorized."

Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
Tip
  • JWTs are commonly stateless (no server-side session lookup needed) — a big architectural difference from traditional session-cookie authentication, which requires the server to store session state somewhere.

API Concepts

21. REST API Basics

REST (Representational State Transfer) is an architectural style for designing APIs around resources (nouns, like /products, /users), manipulated using standard HTTP methods. A RESTful API should be stateless (no server-side session per request) and use predictable, resource-oriented URLs.

GET    /products        → list products
GET    /products/42      → get one product
POST   /products         → create a product
PUT    /products/42      → replace a product
PATCH  /products/42      → partially update a product
DELETE /products/42      → delete a product

22. CRUD Operations

CRUDHTTP Method
CreatePOST
ReadGET
UpdatePUT / PATCH
DeleteDELETE

23. Idempotency

An operation is idempotent if performing it multiple times produces the same result as performing it once. GET, PUT, and DELETE are expected to be idempotent; POST generally is not (calling it twice typically creates two records).

MethodIdempotent?
GETYes
PUTYes
DELETEYes
PATCHIdeally, but depends on implementation
POSTNo
Practical relevance: idempotency matters a lot for retry logic — it's safe to automatically retry a failed GET or DELETE request, but retrying a failed POST (e.g., "create order") without idempotency protection could create duplicate orders.

24. Error Handling

A well-designed API returns errors with a correct status code and a consistent, informative body — not just a generic 500 for everything.

{
  "status": "fail",
  "message": "Product with id 42 not found"
}
Tip
  • Distinguish operational errors (expected, like "not found" or "validation failed" — return 4xx) from programming errors (bugs — return 500 and log them for investigation, without leaking internal details to the client).

25. API Versioning

As an API evolves, versioning prevents breaking existing clients when introducing changes.

/api/v1/products
/api/v2/products

Common strategies: URL path versioning (as above), header-based versioning (Accept: application/vnd.myapp.v2+json), or query parameter versioning (?version=2) — URL path versioning is the most common in practice due to its simplicity and visibility.

Level Six

Performance & Advanced Protection

26. CORS (Cross-Origin Resource Sharing)

A browser security mechanism that blocks a web page from making requests to a different origin (domain/port/protocol) than the one it was served from, unless that other server explicitly allows it via response headers.

Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Important: CORS is enforced by the browser, not the server — it doesn't protect the server from non-browser clients (like Postman or curl), which ignore CORS entirely. It exists purely to protect users' browsers from malicious cross-site scripts.

27. Caching

Storing a response so subsequent identical requests can be served faster, without hitting the server (or the origin server) again.

HeaderPurpose
Cache-Control: max-age=3600Cache this response for 3600 seconds
ETagA fingerprint of the resource; used to check if it changed
304 Not ModifiedServer tells the client its cached copy is still valid

28. Rate Limiting

Restricting how many requests a client can make in a given time window, to protect the server from abuse or overload.

HTTP/1.1 429 Too Many Requests
Retry-After: 60

Commonly implemented with middleware (e.g., express-rate-limit in Node.js) tracking request counts per IP or per API key.

29. Compression (Gzip/Brotli)

The server compresses the response body before sending it, and the client decompresses it — reducing the amount of data transferred over the network.

Request:  Accept-Encoding: gzip, br
Response: Content-Encoding: gzip

30. Keep-Alive & Persistent Connections

By default in HTTP/1.1, a single TCP connection stays open across multiple requests/responses instead of opening a brand-new connection for every single request — avoiding the overhead of repeated TCP handshakes.

Connection: keep-alive

Practical Tools

31. File Uploads (multipart/form-data)

Uploading files (images, documents) requires a special content type that can carry both regular fields and binary file data in a single request body, each part separated by a boundary marker.

Content-Type: multipart/form-data; boundary=----WebKitFormBoundary

------WebKitFormBoundary
Content-Disposition: form-data; name="title"

Laptop HP
------WebKitFormBoundary
Content-Disposition: form-data; name="image"; filename="laptop.png"
Content-Type: image/png

[binary data]
------WebKitFormBoundary--

In Express.js, this is typically handled with a middleware like multer.

32. Fetch API / Axios (Client-Side Requests)

// Fetch API (built into browsers)
const res = await fetch("https://api.example.com/products/42");
const data = await res.json();

// Axios (popular third-party library)
const { data } = await axios.get("https://api.example.com/products/42");
Axios automatically parses JSON and throws on non-2xx status codes by default; Fetch does neither — a 404 response from fetch() doesn't throw an error unless you check res.ok manually.

33. API Testing (Postman / Thunder Client)

Tools that let you manually construct and send HTTP requests (setting method, headers, body) without writing client code — essential for testing an API independently of the frontend that will eventually consume it.

Tip
  • Use Postman/Thunder Client collections to save common requests (with environment variables for base URLs and tokens), making it easy to re-test endpoints as the API evolves.

34. Browser Developer Tools (Network Tab)

The Network tab in browser DevTools shows every request the page makes — method, status code, headers, request/response bodies, and timing — invaluable for debugging why a frontend isn't getting the data it expects.

35. WebSockets vs. HTTP

HTTPWebSockets
Connection modelRequest-response, typically short-lived per exchangeA single persistent, full-duplex connection
Who can initiateOnly the clientEither side can send messages at any time
Typical useStandard API calls, page loadsReal-time features — chat apps, live notifications, live dashboards
Overhead per messageHigher (new headers each time, unless Keep-Alive is used)Lower — no repeated handshake once connected
How it starts: a WebSocket connection begins as a normal HTTP request that includes an Upgrade: websocket header; if the server agrees, the connection "upgrades" from HTTP to the WebSocket protocol and stays open for ongoing bidirectional communication.
