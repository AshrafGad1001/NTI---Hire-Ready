Section One

Lean Queries — .lean() and When to Use It

By default, Mongoose wraps every query result in full Mongoose Document instances — objects with change-tracking, getters/setters, virtuals, and instance methods attached. .lean() skips all of that and returns plain JavaScript objects instead.

// Without lean() - full Mongoose Document
const user = await User.findById(id);
user.isModified("name");   // works - it's a real Document
await user.save();          // works

// With lean() - plain JS object, much lighter
const user = await User.findById(id).lean();
user.isModified;   // undefined - lean objects have no Document methods
// user.save() would throw — it's not a Document at all

A Real-World Example — A Read-Only Listing Endpoint

// This endpoint only displays data — never modifies it
app.get("/trainees", async (req, res) => {
  const trainees = await User
    .find({ role: "trainee", isActive: true })
    .select("name track completedCourses")
    .lean();   // significant performance win here

  res.json({ status: "success", data: trainees });
});
Without .lean()With .lean()
Return typeFull Mongoose DocumentPlain JavaScript object
Has virtuals/gettersYesNo (unless manually re-applied)
Can call .save()YesNo
Memory & CPU overheadHigherLower — often noticeably faster on large result sets
When NOT to use .lean(): if you need to call .save(), rely on virtuals, use instance methods, or need Mongoose's automatic type casting/getters applied to the result, skip .lean() for that particular query.

Section Two

Indexes in Mongoose & Building Indexes in Production

As covered at the MongoDB level, indexes dramatically speed up reads at the cost of slower writes and extra storage. Mongoose lets you declare them directly in the schema.

userSchema.index({ email: 1 }, { unique: true });
userSchema.index({ role: 1, track: 1, isActive: 1 });   // compound index for common admin filters

The Production Concern — Automatic Index Building

By default, Mongoose calls createIndex() automatically for every declared index whenever the application connects — this is convenient in development, but risky in production on large collections.

Why this matters: building an index on a large, already-populated collection can be slow and resource-intensive. If it happens automatically every time your app restarts in production, it can cause unexpected load spikes or delays at startup.
// Disable automatic index building in production
mongoose.set("autoIndex", process.env.NODE_ENV !== "production");

Real-World Example — Building Indexes Explicitly via a Migration Script

// scripts/build-indexes.js
const mongoose = require("mongoose");
const User = require("../models/User");
const Product = require("../models/Product");

async function buildIndexes() {
  await mongoose.connect(process.env.MONGO_URI);
  await User.createIndexes();
  await Product.createIndexes();
  console.log("Indexes built successfully");
  await mongoose.connection.close();
}

buildIndexes();

This script is run deliberately (e.g., during a deployment step), rather than silently on every app startup — giving you control over exactly when the potentially expensive index-building operation happens.

Transactions with Mongoose

This connects directly to the MongoDB Transactions concepts covered earlier — Mongoose provides a thin, convenient wrapper around the same underlying session-based transaction API.

Real-World Example — The Cash Order Checkout, Revisited with Mongoose Sessions

const createCashOrder = async (req, res) => {
  const session = await mongoose.startSession();
  session.startTransaction();

  try {
    const cart = await Cart.findById(req.params.cartId).session(session);

    const order = await Order.create(
      [{
        user: req.user._id,
        cartItems: cart.cartItems,
        totalOrderPrice: cart.totalPriceAfterDiscount || cart.totalPrice,
        paymentMethodType: "cash"
      }],
      { session }
    );

    const bulkOptions = cart.cartItems.map((item) => ({
      updateOne: {
        filter: { _id: item.product, quantity: { $gte: item.quantity } },
        update: { $inc: { quantity: -item.quantity, sold: +item.quantity } }
      }
    }));

    const bulkResult = await Product.bulkWrite(bulkOptions, { session });

    if (bulkResult.modifiedCount !== cart.cartItems.length) {
      throw new Error("Insufficient stock for one or more products");
    }

    await Cart.findByIdAndDelete(req.params.cartId).session(session);

    await session.commitTransaction();
    res.status(201).json({ status: "success", data: order });
  } catch (error) {
    await session.abortTransaction();
    res.status(400).json({ status: "fail", message: error.message });
  } finally {
    session.endSession();
  }
};

A Reusable Transaction Wrapper Pattern

async function withTransaction(operationFn) {
  const session = await mongoose.startSession();
  session.startTransaction();
  try {
    const result = await operationFn(session);
    await session.commitTransaction();
    return result;
  } catch (error) {
    await session.abortTransaction();
    throw error;
  } finally {
    session.endSession();
  }
}

// Usage:
await withTransaction(async (session) => {
  await Order.create([orderData], { session });
  await Product.updateMany(filter, update, { session });
});
Reminder from the MongoDB-level coverage: transactions still require a replica set or sharded cluster underneath, and every operation inside must pass { session } explicitly — Mongoose doesn't do this automatically just because you're inside a try block.

Connection Pooling & Performance Tuning

Beyond the basic pooling covered earlier, production tuning involves matching pool size and timeouts to your actual traffic patterns.

mongoose.connect(process.env.MONGO_URI, {
  maxPoolSize: 20,                   // higher for high-concurrency production traffic
  minPoolSize: 5,
  socketTimeoutMS: 45000,             // how long a socket can stay idle before closing
  serverSelectionTimeoutMS: 5000,     // how long to wait for a server to become available
  heartbeatFrequencyMS: 10000         // how often the driver checks server status
});
SettingPurposeTuning Consideration
maxPoolSizeMaximum concurrent connectionsToo low → requests queue waiting for a free connection; too high → can overwhelm the DB server
minPoolSizeConnections kept open even when idleHigher values reduce cold-start latency for sudden traffic bursts
socketTimeoutMSHow long an idle socket stays openToo short can cause premature disconnects on slow queries
serverSelectionTimeoutMSHow long to wait before failing over connectivity issuesLower values fail faster but may be too aggressive on flaky networks
Tip
  • Monitor actual connection pool usage in production (via MongoDB Atlas metrics or db.serverStatus().connections) before tuning these numbers blindly — start from real traffic data, not guesswork.

Section Five

Best Practices & Tips for This Level

1. Default to .lean() on Any Read-Only List Endpoint

Any endpoint that only displays data (never calls .save() on the result) is a strong candidate for .lean() — this adds up significantly on high-traffic listing pages.

2. Disable autoIndex in Production, Build Indexes Deliberately

Use mongoose.set("autoIndex", false) in production and run index creation explicitly as part of your deployment process instead.

3. Wrap Multi-Step Financial or Inventory Operations in Transactions

As covered — anything touching stock, balances, or multiple related collections that must succeed or fail together belongs in a transaction, using the reusable wrapper pattern to avoid repeating boilerplate.

4. Tune Connection Pool Settings Based on Observed Traffic, Not Assumptions

Start with sensible defaults, then adjust maxPoolSize and timeouts based on actual production monitoring data.

5. Combine .select() with .lean() for Maximum Read Efficiency

const trainees = await User
  .find({ role: "trainee" })
  .select("name track completedCourses")
  .lean();

This reduces both the data transferred from MongoDB and the in-memory JS object overhead simultaneously.

Extra Tips & Tricks
  • Remember that .lean() results won't include virtuals unless you manually attach them — if a listing endpoint depends on a virtual field, either compute it manually after the lean query or skip .lean() for that specific case.
  • For transaction-heavy workloads, keep each transaction's scope as small and fast as possible — avoid slow external calls (emails, third-party APIs) inside the transaction block itself; trigger those after a successful commit instead.
  • When running index-build scripts in production, schedule them during lower-traffic windows if the collection is large, since building can still temporarily affect performance even when run deliberately.
