Section One

Mongoose Plugins — Reusing Logic Across Schemas

A plugin is a reusable function that attaches shared fields, methods, or middleware to any schema it's applied to — useful when the same pattern (like soft delete or pagination metadata) repeats across many models.

Real-World Example — A Reusable Soft Delete Plugin

// plugins/softDelete.js
function softDeletePlugin(schema) {
  schema.add({
    isDeleted: { type: Boolean, default: false },
    deletedAt: { type: Date, default: null }
  });

  schema.pre(/^find/, function(next) {
    this.where({ isDeleted: { $ne: true } });
    next();
  });

  schema.methods.softDelete = function() {
    this.isDeleted = true;
    this.deletedAt = new Date();
    return this.save();
  };
}

module.exports = softDeletePlugin;
// models/User.js
const softDeletePlugin = require("../plugins/softDelete");

const userSchema = new Schema({ name: String, email: String });
userSchema.plugin(softDeletePlugin);

module.exports = mongoose.model("User", userSchema);
// models/Product.js
const softDeletePlugin = require("../plugins/softDelete");

const productSchema = new Schema({ title: String, price: Number });
productSchema.plugin(softDeletePlugin);   // same reusable logic, different schema

module.exports = mongoose.model("Product", productSchema);

Applying a Plugin Globally to Every Schema

// If every model in the app should have this behavior
mongoose.plugin(softDeletePlugin);
Why this matters: without a plugin, adding soft-delete behavior to five different models means copy-pasting the same fields and middleware five times — any future change (e.g., adding a "deletedBy" field) then requires updating every copy. A plugin centralizes it in one place.

Section Two

TypeScript with Mongoose

Mongoose provides built-in TypeScript support, letting you type both the document shape and the model's static/instance methods.

A Typed Schema and Model

import { Schema, model, Document, Model } from "mongoose";

interface IUser {
  name: string;
  email: string;
  role: "trainee" | "mentor" | "admin";
  isActive: boolean;
}

interface IUserDocument extends IUser, Document {
  // instance methods go here
  isInStock?(): boolean;
}

interface IUserModel extends Model {
  // static methods go here
  findByEmail(email: string): Promise;
}

const userSchema = new Schema({
  name: { type: String, required: true },
  email: { type: String, required: true },
  role: { type: String, enum: ["trainee", "mentor", "admin"], default: "trainee" },
  isActive: { type: Boolean, default: true }
});

userSchema.statics.findByEmail = function(email: string) {
  return this.findOne({ email });
};

const User = model("User", userSchema);

export default User;

Using the Typed Model

const user = await User.findByEmail("ashraf@test.com");
// TypeScript knows "user" is IUserDocument | null, with full autocomplete

if (user) {
  console.log(user.role);   // typed as "trainee" | "mentor" | "admin"
}
Tip
  • Keep the plain data interface (IUser) separate from the Document interface (IUserDocument) — this makes it easy to reuse the plain shape elsewhere (e.g., in a DTO for an API response) without dragging in Mongoose-specific Document behavior.

Testing with Mongoose — Mocking & mongodb-memory-server

Testing code that touches a real database has two common approaches: mocking Mongoose entirely, or running tests against a real (but temporary, in-memory) MongoDB instance.

Approach 1 — mongodb-memory-server (Recommended for Most Cases)

This spins up an actual, temporary MongoDB instance in memory for the duration of the test suite — giving you real Mongoose behavior (validation, middleware, indexes) without needing a persistent database or extensive mocking.

// test-setup.js
const { MongoMemoryServer } = require("mongodb-memory-server");
const mongoose = require("mongoose");

let mongoServer;

beforeAll(async () => {
  mongoServer = await MongoMemoryServer.create();
  const uri = mongoServer.getUri();
  await mongoose.connect(uri);
});

afterEach(async () => {
  const collections = mongoose.connection.collections;
  for (const key in collections) {
    await collections[key].deleteMany();
  }
});

afterAll(async () => {
  await mongoose.connection.close();
  await mongoServer.stop();
});

Real-World Example — Testing User Creation and Validation

const User = require("../models/User");

describe("User Model", () => {
  it("should create a user with valid data", async () => {
    const user = await User.create({
      name: "Ashraf",
      email: "ashraf@test.com",
      role: "trainee"
    });

    expect(user.email).toBe("ashraf@test.com");
  });

  it("should fail validation without a required email", async () => {
    await expect(
      User.create({ name: "Ashraf" })
    ).rejects.toThrow();
  });

  it("should reject a duplicate email", async () => {
    await User.create({ name: "A", email: "dup@test.com" });
    await expect(
      User.create({ name: "B", email: "dup@test.com" })
    ).rejects.toThrow();
  });
});

Approach 2 — Mocking Mongoose Entirely (Faster, but Less Realistic)

jest.mock("../models/User");

const User = require("../models/User");

it("calls User.create with the right data", async () => {
  User.create.mockResolvedValue({ _id: "123", name: "Ashraf" });

  const result = await createUserService({ name: "Ashraf" });

  expect(User.create).toHaveBeenCalledWith({ name: "Ashraf" });
  expect(result._id).toBe("123");
});

Section Four

Best Practices & Tips for This Level

1. Extract Repeated Schema Behavior into a Plugin Early

The moment you notice the same fields/middleware being copy-pasted across two or more schemas (soft delete, audit timestamps, versioning), that's the signal to extract a plugin.

2. Keep Plain Data Interfaces Separate from Document Interfaces in TypeScript

As shown in Section Two — this keeps your typing flexible for use outside the Mongoose layer (API responses, DTOs) without unnecessary coupling.

3. Prefer mongodb-memory-server for Anything Testing Schema-Level Behavior

Validation rules, middleware, unique indexes, and aggregation pipelines are exactly the kind of behavior that mocking can't meaningfully verify — use a real (if temporary) database for these tests.

4. Reserve Mocking for True Unit Tests of Business Logic

When testing a service function's decision-making logic in isolation, and the actual database interaction isn't what's being verified, mocking keeps tests fast and focused.

5. Clean Up Test Data Between Tests, Not Just at the End of the Suite

As shown in the afterEach hook — clearing collections after every test prevents one test's leftover data from silently affecting the next test's assertions.

Extra Tips & Tricks
  • When writing a plugin, use schema.add() for new fields rather than modifying the schema object directly — it keeps the plugin composable and less likely to conflict with fields the consuming schema already defines.
  • In TypeScript, avoid using any for the Model's generic type "just to make the errors go away" — it silently disables the exact safety net you're integrating TypeScript for in the first place.
  • mongodb-memory-server downloads a real MongoDB binary on first run — cache it in CI environments to avoid repeated downloads slowing down every pipeline run.
  • When testing middleware specifically (like a pre-save hook), write a test that asserts the hook's *effect* (e.g., password ends up hashed) rather than trying to spy on the internal hook function itself — this keeps tests resilient to internal refactors.
