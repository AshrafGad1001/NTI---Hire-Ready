Topic One

SQL Mindset vs. NoSQL Mindset

SQL: Think "Normalization" First

The philosophy: split data into the smallest possible units, avoid any duplication, and link everything with Foreign Keys. This decision is made while designing the tables — often before you even know which queries will run against them.

-- SQL: three separate tables, linked by Foreign Keys
Users (id, name, email)
Orders (id, user_id, date)
OrderItems (id, order_id, product_id, quantity)

Whenever a query needs combined data, you run a JOIN at query time.

NoSQL: Think "Query Patterns" First

The philosophy: design the schema around how you'll read the data, not around how "clean" it looks in theory. The question isn't "what's the correct relationship between the data?" — it's "what query will run most often, and how do I make it fast?"

// NoSQL: order data and its related product info are grouped together
{
  _id: 1,
  user: { name: "Ashraf", email: "..." },  // Embedded
  date: "...",
  items: [
    { productName: "Laptop", quantity: 1, price: 15000 }
  ]
}

No JOIN needed at read time — everything is already available in a single document.

The Core Difference

SQLNoSQL
Starting pointRelationships between entitiesActual queries that will run (access patterns)
Primary goalAvoid data duplication (integrity)Read performance
Schema flexibilityFixed, hard to migrateFlexible — add fields to any document independently
Decision timingTables designed first, queries come laterQueries must be known first, then the schema is designed
Most common mistake: bringing the full SQL mindset into NoSQL — referencing everything like Foreign Keys and joining ($lookup) on every query. The result is poor performance, because you lose NoSQL's biggest advantage: keeping related data together from the start.
Tip
  • Golden rule: "Data that is accessed together should be stored together."
  • Before writing a single line of schema code, write down the top 5–10 queries your app will actually run.
  • If you find yourself justifying a schema decision with "because that's how it'd work in SQL," stop and re-check against your access patterns.

Topic Two

Design Pattern 1 — Embedding

The idea: place related data directly inside the same document, instead of a separate collection.

{
  _id: 1,
  name: "Ashraf",
  addresses: [
    { city: "Shebin El-Kom", street: "Main St", isDefault: true },
    { city: "Cairo", street: "Nasr City", isDefault: false }
  ]
}

When to Use It

  • The relationship is one-to-few (e.g., a user has 2–3 addresses, not thousands).
  • The related data is almost always read together (there's no scenario where you fetch the user without their addresses).
  • The data doesn't change frequently or independently of the parent.

Pros

  • A single query retrieves everything (no $lookup needed).
  • Excellent read performance.
  • Atomic updates — parent and embedded data update together in one operation.

Cons

  • If the array grows too large, the document size grows with it (risking the 16MB limit).
  • If the embedded data is shared across multiple parents, duplication occurs.
Tips & Tricks
  • A good rule of thumb: embed when the array size is bounded and predictable (rarely exceeds a few dozen items).
  • If you're unsure whether to embed, ask: "Will I ever need this child data without its parent?" If no — embed.
  • Embedding read-only "snapshot" data (e.g., a price at time of purchase) is safe even if the source can change later — see the Computed/Snapshot note in the Common Mistakes section.

Topic Three

Design Pattern 2 — Referencing

The idea: store just a reference (ID) instead of the full data, similar to a Foreign Key.

// in users
{ _id: 1, name: "Ashraf" }

// in projects
{ _id: 101, title: "GoRent", ownerId: 1 }

When to Use It

  • The relationship is a large one-to-many or many-to-many.
  • The related data changes frequently and independently of the other side.
  • The related data is shared across multiple documents (e.g., one product referenced by many orders).
  • The array could grow without bound (e.g., a very large number of comments).

Pros

  • Documents stay small and organized.
  • Updating shared data (e.g., a user's profile) only requires updating one place.
  • No data duplication.

Cons

  • Requires a $lookup (like a JOIN) at read time — slower than embedding.
  • Not atomic — updating two related documents together requires a transaction.
Tips & Tricks
  • Always index the field you're referencing by (e.g., ownerId), since it's effectively your "foreign key lookup" field.
  • If you find yourself doing $lookup on the same field in almost every query, consider whether a Subset or Computed pattern could reduce that need.
  • Two-way referencing (both sides store each other's IDs) is fine for many-to-many, as long as you pick a clear "primary" side to update first in your application logic.

Topic Four

Design Pattern 3 — Subset Pattern

The idea: instead of fully embedding or fully referencing, use a middle ground — store only a small portion of the related data (e.g., the most recent/most relevant items), while the full data lives in a separate collection with a reference.

// Product document holds only the latest 5 reviews, not all of them
{
  _id: 1,
  title: "Laptop HP",
  price: 15000,
  recentReviews: [   // Subset only — latest 5
    { user: "Sara", rating: 5, comment: "Great!" },
    { user: "Omar", rating: 4, comment: "Good" }
  ],
  totalReviewsCount: 230  // pre-computed total
}

// The full set of reviews lives in a separate collection
db.reviews.find({ productId: 1 })

When to Use It

When you have a large amount of related data (like reviews), but you also need a small portion of it to appear instantly alongside the parent (e.g., showing the latest 3 ratings on a product page without an extra query).

Practical example: in an e-commerce API, this is the ideal solution for displaying "latest 3 reviews" on a product page without running an aggregation on every page load.
Tips & Tricks
  • Keep the subset small and purpose-built (e.g., "latest 3–5 items") — it's a display optimization, not a full copy.
  • Update the subset only when new data is added to the full collection (e.g., a background job or an application-level trigger), not on every read.
  • Combine this pattern with the Computed Pattern: store both a small subset (recentReviews) and a pre-calculated aggregate (averageRating) side by side.

Topic Five

Design Pattern 4 — Bucket Pattern

The idea: instead of creating a separate document for every single reading/event, group a batch of readings from the same time window into one document — commonly used with time-series data.

// Instead of one document per second (thousands of documents)
// group all readings for one hour into a single document
{
  sensorId: "sensor_001",
  date: "2026-07-12",
  hour: 14,
  readings: [
    { minute: 0, temp: 25.3 },
    { minute: 1, temp: 25.5 },
    { minute: 2, temp: 25.4 }
    // ... rest of the hour's minutes
  ],
  avgTemp: 25.4,
  maxTemp: 26.1,
  minTemp: 24.8
}

When to Use It

  • Time-series data (IoT sensor readings, logs, analytics events).
  • A massive number of closely-spaced-in-time readings.

Pros

  • Dramatically reduces the total number of documents (thousands instead of millions).
  • Indexes stay smaller and faster.
  • Easy to pre-compute aggregates (avg, max, min) and store them inside the bucket itself.
Tips & Tricks
  • Pick a bucket window (hour, day) based on your query patterns — how granular do reads actually need to be?
  • MongoDB's native Time Series Collections (available since v5.0) automate much of this pattern — worth checking if your MongoDB version supports it before hand-rolling buckets.
  • Watch out for buckets that grow unbounded within the time window if the event rate spikes unexpectedly.

Topic Six

Design Pattern 5 — Computed Pattern

The idea: instead of recalculating a value every time it's requested (e.g., averaging all reviews on every page load), calculate it once and store it as a ready-made field, updating it only when the underlying data changes.

// Instead of running an aggregation every time the product page loads
{
  _id: 1,
  title: "Laptop HP",
  price: 15000,
  averageRating: 4.5,     // pre-computed
  totalReviews: 230       // pre-computed
}

// When a new review is added, only these two fields get updated —
// not recalculated from all 230 reviews on every page view

When to Use It

  • A calculation is read very frequently (every time a product page opens) but changes relatively rarely (a new review every so often).
  • You want to avoid an expensive aggregation (e.g., averaging across thousands of documents) on every request.
Practical example: in an e-commerce API, instead of running the aggregation pipeline that computes avgRating every time a product page loads, store the result directly on the Product document and update it only when a review is added or removed.
Tips & Tricks
  • Update computed fields via application logic right after the write that changes them (e.g., inside the same request that creates a review), not through a separate cron job unless near-real-time accuracy isn't required.
  • For high write volume, consider using MongoDB transactions to keep the computed field and the source data consistent.
  • This pattern trades a small amount of write complexity for a large gain in read performance — worth it wherever reads vastly outnumber writes.

Topic Seven

Relationship Types

One-to-One

One entity is linked to exactly one entity of another type.

// A user and their detailed profile info (rarely read together)
{ _id: 1, name: "Ashraf", profileDetails: { bio: "...", cv: "..." } }

Decision: usually embed, unless the data is very large or rarely read alongside the parent.

One-to-Few

One entity is linked to a small number (2–100) of entities of another type.

// A user and their addresses (2–3 addresses)

Decision: Embed — the count is small and stable.

One-to-Many

One entity is linked to a relatively large number (hundreds to thousands) of entities of another type.

// A category and its products (could be thousands)

Decision: Reference, usually — the count is large and constantly changing.

One-to-Squillions

One entity is linked to a massive (millions) number of entities of another type.

// A single server and its millions of log entries

Decision: Referencing is mandatory — likely combined with the Bucket Pattern to reduce document count.

Many-to-Many

Each entity of one type can be linked to multiple entities of the other type, and vice versa.

// Students and Courses — each student is enrolled in several courses,
// and each course has many students
{ _id: 1, name: "Ashraf", enrolledCourseIds: [101, 102, 103] }
{ _id: 101, title: "React Basics", enrolledStudentIds: [1, 5, 9] }

Decision: usually two-way referencing, or referencing from a single direction based on which direction is queried more often.

Tips & Tricks
  • When in doubt about a relationship's cardinality, estimate the maximum realistic count over the object's lifetime — that number alone often decides between embed and reference.
  • For many-to-many, if one direction is queried far more often than the other, consider referencing only in that direction and using a $lookup for the rare reverse query instead of maintaining both arrays.

Topic Eight

The Schema Design Process (Steps 1–4)

Step 1 — Identify the Entities

Write a list of every core "thing" in your system.

Example: User, Product, Order, Review, Category

Step 2 — Identify the Most Common Queries (Access Patterns)

This is the most important step in NoSQL design. Before writing any schema, ask yourself:

  • What query will run most often? (e.g., "get all products in a given category")
  • What actions do users perform frequently? (e.g., "open a product page, view its reviews")
  • What's the read-to-write ratio? Is this workload read-heavy or write-heavy?

Write these queries down explicitly before designing anything:

1. Get all products in a category, sorted by price
2. Get a single product with its latest 5 reviews
3. Get all orders for a specific user
4. Search products by name

Step 3 — Identify the Relationships Between Entities

For each pair of entities, determine the type (one-to-one, one-to-few, one-to-many, many-to-many).

User → Orders: One-to-Many
Order → Products: Many-to-Many
Product → Reviews: One-to-Squillions

Step 4 — Apply the Right Pattern to Each Relationship

Ask three questions for every relationship:

  1. Growth rate — is the count small and stable, or large and increasing?
  2. Update frequency — does the data change often, or rarely?
  3. Read-together frequency — is the child data needed every time the parent is fetched?

Based on the answers, choose: Embed / Reference / Subset / Bucket / Computed.

Tips & Tricks
  • Keep your access-pattern list as a living document — revisit it whenever a new feature changes how data is queried.
  • It's fine to mix patterns within the same schema — e.g., embed addresses, reference orders, and use a computed field for ratings, all in the same User/Product design.
  • When two access patterns conflict (one favors embedding, another favors referencing), prioritize whichever query runs more frequently or is more performance-critical for the user experience.

Topic Nine

Step 5 — Avoiding Common Mistakes

This isn't a "design" step — it's a review and critique step. After designing a schema, go back and check it against these common pitfalls.

Mistake 1 — Unbounded Arrays

// ❌ Very common mistake
{
  productId: 1,
  reviews: [ /* thousands of reviews embedded directly in the product */ ]
}

Problem: this will eventually hit the 16MB limit, and the document becomes slow to read and write well before that limit is even reached.

Fix: use Referencing or the Subset Pattern instead.

Mistake 2 — Deeply Nested Documents

// ❌ Common mistake
{
  user: {
    profile: {
      settings: {
        preferences: {
          notifications: {
            email: { enabled: true }
          }
        }
      }
    }
  }
}

Problem: deeply nested fields are hard to update, and queries become unwieldy (user.profile.settings.preferences.notifications.email.enabled).

Fix: try to keep nesting to 2–3 levels at most.

Mistake 3 — Over-Embedding to "Avoid SQL-Style Joins"

This is the most dangerous mistake — beginners often feel that every embed is a "performance win," so they embed everything even when it doesn't make sense.

// ❌ Mistake — embedding data that changes constantly and is shared across many documents
{
  orderId: 1,
  productDetails: { name: "Laptop", price: 15000, stock: 45 }  // full copy of product data
}

Problem: if the product's price changes, you'd need to update every past order containing that product — a disaster.

Fix: the order should store only a snapshot of relevant data at the moment of purchase (e.g., the price at sale time), not a live copy that's expected to stay in sync with changes.

Key distinction: embedding a snapshot (immutable, point-in-time data) is safe and often correct. Embedding a live copy of mutable data that's also stored elsewhere is the actual mistake.
Tips & Tricks
  • Before finalizing any schema, explicitly write "is this field a snapshot or a live copy?" next to every embedded object that duplicates data from elsewhere.
  • Run db.collection.find(...).explain("executionStats") against your top access-pattern queries to catch accidental COLLSCANs early.
  • Periodically check actual document sizes in production (db.collection.stats()) — unbounded arrays often creep up slowly before becoming a real problem.

Topic Ten

Step 6 — Auditing a Real Project

This is a real, practical application step — not a hypothetical exercise. Take an actual schema from a live project you've built (e.g., GoRent or an e-commerce API) and run a full audit on it.

How to Run the Audit

  1. Open every schema you have (Product, Order, Review, etc.).
  2. For each one, ask: "Why did I choose to embed here? Why did I choose to reference there?" If the honest answer is "I'm not sure, it just felt easier at the time," that decision was made without real analysis.
  3. Go back to your project's real access-pattern list — what queries actually run often on the live site?
  4. Compare: does the current schema serve those queries efficiently, or is it doing unnecessary $lookups?
Possible real example: in an e-commerce API, if the Review schema fully references both Product and User, and every fetch runs two $lookups — it's worth asking whether the Computed Pattern would be a better fit, storing a ready-made averageRating directly on the Product instead of recalculating it via aggregation every time.
Tips & Tricks
  • Turn the audit into a recurring habit — revisit schemas every few months as usage patterns evolve, not just once at project launch.
  • Use MongoDB's $indexStats aggregation stage to see which indexes are actually being used in production — drop the ones that aren't.
  • Document each schema decision with a one-line comment in code (e.g., // embedded: 1-to-few, always read together) so future-you (or teammates) understand the reasoning without re-deriving it.
  • When migrating a schema decision (e.g., from embed to reference), plan a data migration script and test it on a copy of production data first.
