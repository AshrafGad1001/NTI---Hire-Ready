Section One

Why Transactions Are Needed

In NoSQL, a single document is inherently atomic — updating one document is guaranteed to happen entirely or not at all. The problem appears when an operation needs to update more than one document across more than one collection at the same time.

The Classic Problem Example

Consider a "purchase a product" operation:

  1. Decrease stock quantity in products
  2. Create a new order in orders
  3. Deduct funds from the user's balance in users
// ❌ Without a transaction — a real risk
await Product.updateOne({ _id: productId }, { $inc: { stock: -1 } });
// The server crashes right here!
await Order.create({ userId, productId, status: "confirmed" });
await User.updateOne({ _id: userId }, { $inc: { balance: -price } });

If the server crashes right after the first step, the result is: stock was decremented, but no order was ever created, and no money was deducted — a product vanished for no reason, and the customer never paid. This is exactly what transactions prevent.

Section Two

How Transactions Solve the Problem (ACID Guarantee)

A transaction guarantees that all these operations execute as a single unit (all or nothing):

  • If everything succeeds → commit (all changes are persisted together)
  • If anything fails at any step → abort (everything is rolled back, including steps that had already succeeded)
const session = await mongoose.startSession();
session.startTransaction();

try {
  await Product.updateOne(
    { _id: productId },
    { $inc: { stock: -1 } },
    { session }
  );

  await Order.create(
    [{ userId, productId, status: "confirmed" }],
    { session }
  );

  await User.updateOne(
    { _id: userId },
    { $inc: { balance: -price } },
    { session }
  );

  await session.commitTransaction();
  console.log("Transaction succeeded");
} catch (error) {
  await session.abortTransaction();
  console.log("Transaction failed, everything rolled back:", error);
} finally {
  session.endSession();
}
Important: every operation must pass the same session as an option, or it won't be treated as part of the same transaction.

Section Three

The Core Steps of Any Transaction

StepCommandPurpose
1startSession()Begins a new session tied to the transaction
2startTransaction()Actually starts the transaction
3Run operations passing { session }Each operation is recorded as part of the transaction, not applied to real data immediately
4commitTransaction()Persists all changes at once
5abortTransaction() (on error)Rolls back everything
6endSession()Closes the session and frees resources

Section Four

Requirements to Run Transactions

Critical: transactions are not available in every MongoDB setup.
  • MongoDB must be running as a Replica Set (even a single-node replica set for local development) or a Sharded Cluster.
  • Not available on a standalone MongoDB instance (a plain server with no replica set).
  • Supported from MongoDB 4.0 onward for replica sets, and from 4.2 onward for sharded clusters.
// For local development, run a single-node replica set:
mongod --replSet rs0
// then initiate it:
rs.initiate()

Attempting to use a transaction on a standalone instance results in a clear error stating the feature isn't supported.

Section Five

Write Conflicts & Retry Logic

If another transaction tries to modify the same document at the same time, MongoDB throws a Write Conflict Error. This is part of the Isolation guarantee in ACID.

try {
  // the operation
} catch (error) {
  if (error.errorLabels && error.errorLabels.includes("TransientTransactionError")) {
    // safe to retry — this error is temporary
  }
  await session.abortTransaction();
}
Best Practice
  • Your code should be prepared to retry when a TransientTransactionError occurs, since it indicates a temporary conflict between transactions, not an actual logic error.
  • MongoDB drivers provide helper wrappers (e.g., withTransaction() in the native driver) that automatically handle retry logic for transient errors — worth using instead of hand-rolling retry loops.

Section Six

Read Concern & Write Concern Inside Transactions

You can control the accuracy-vs-speed trade-off explicitly:

session.startTransaction({
  readConcern: { level: "snapshot" },     // read a fixed snapshot of data as of transaction start
  writeConcern: { w: "majority" }         // writes must be acknowledged by a majority of nodes before success
});

readConcern: "snapshot" matters a lot because it guarantees you're reading the same version of the data throughout the transaction's lifetime, even if someone else modifies the data at the same moment.

Section Seven

When to Use Transactions (and When Not To)

Use Them When:

  • An operation touches more than one collection and all parts must succeed or fail together (like the purchase example above).
  • Financial operations (transferring balance, deducting/adding credit).
  • Operations with a serious race condition risk (e.g., booking the last available ticket or the last item in stock).

Avoid Them When:

  • The operation touches a single document only — MongoDB documents are already atomic, so an extra transaction adds nothing.
  • You have very high throughput (many operations per second) — transactions add noticeable performance overhead.
  • The problem can be solved with a better schema design instead (e.g., embedding) rather than needing coordination across separate collections in the first place.

Section Eight

Real-World Example — Cash Order Checkout

In an e-commerce API, the Cash Order scenario is one of the best real-world fits for a transaction.

const createCashOrder = async (req, res) => {
  const session = await mongoose.startSession();
  session.startTransaction();

  try {
    const cart = await Cart.findById(req.params.cartId).session(session);

    const order = await Order.create(
      [{
        user: req.user._id,
        cartItems: cart.cartItems,
        totalOrderPrice: cart.totalPriceAfterDiscount || cart.totalPrice,
        paymentMethodType: "cash"
      }],
      { session }
    );

    const bulkOptions = cart.cartItems.map((item) => ({
      updateOne: {
        filter: { _id: item.product, quantity: { $gte: item.quantity } },
        update: { $inc: { quantity: -item.quantity, sold: +item.quantity } }
      }
    }));

    const bulkResult = await Product.bulkWrite(bulkOptions, { session });

    // If any product didn't have enough stock, bulkWrite won't update it at all
    if (bulkResult.modifiedCount !== cart.cartItems.length) {
      throw new Error("Insufficient stock for one or more products");
    }

    await Cart.findByIdAndDelete(req.params.cartId).session(session);

    await session.commitTransaction();
    res.status(201).json({ status: "success", data: order });
  } catch (error) {
    await session.abortTransaction();
    res.status(400).json({ status: "fail", message: error.message });
  } finally {
    session.endSession();
  }
};
Why this matters here specifically: if any error occurs after the order was already created (e.g., a stock update failure), without a transaction the customer could end up with a confirmed order while the product was never actually deducted from stock — a genuine data inconsistency.

Section Nine

The Performance Cost of Transactions

Transactions aren't "free" — they take longer than regular operations and hold resources on the server until they're closed (commit/abort). Using them for every simple operation without real need will negatively affect overall system performance.

Golden Rule
  • Only use a transaction when you genuinely need an "all or nothing" guarantee across more than one document/collection — not as a default solution for every update.
  • Keep transactions short-lived: avoid slow operations (like external API calls or heavy computation) inside a transaction block, since long-running transactions hold locks longer and increase the chance of write conflicts with other operations.
  • For single-document updates, rely on MongoDB's built-in document-level atomicity — no transaction wrapper needed.
