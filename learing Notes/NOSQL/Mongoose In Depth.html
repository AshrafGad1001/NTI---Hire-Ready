Section One

Schema — Beyond Just Defining Fields

Basic Definition

const mongoose = require("mongoose");

const productSchema = new mongoose.Schema({
  title: {
    type: String,
    required: [true, "Product title is required"],
    trim: true,
    minlength: 3,
    maxlength: 100
  },
  price: {
    type: Number,
    required: true,
    min: 0
  },
  category: {
    type: mongoose.Schema.Types.ObjectId,
    ref: "Category",
    required: true
  }
}, {
  timestamps: true   // automatically adds createdAt and updatedAt
});

Section Two

Important Schema Options Often Overlooked

const productSchema = new mongoose.Schema({
  // ... fields
}, {
  timestamps: true,

  toJSON: { virtuals: true },     // makes virtuals appear when converted to JSON
  toObject: { virtuals: true },

  strict: true,      // (default: true) — any field not defined in the schema is ignored automatically

  versionKey: false, // removes the __v field Mongoose adds automatically for version tracking

  collection: "products"  // manually set the collection name (if different from default)
});
Important note on "strict": setting it to false means any field on the document not defined in the schema gets saved anyway — this defeats one of the schema's most valuable protections (guarding against unexpected data). Keep it true unless you have a strong reason not to.

Section Three

Instance Methods vs. Static Methods vs. Virtuals

Instance Methods — Operate on a Single Document

productSchema.methods.isInStock = function() {
  return this.quantity > 0;
};

// Usage:
const product = await Product.findById(id);
if (product.isInStock()) { ... }

Static Methods — Operate on the Model Itself

productSchema.statics.findByCategory = function(categoryId) {
  return this.find({ category: categoryId });
};

// Usage:
const products = await Product.findByCategory(categoryId);

Virtuals — Computed Fields, Not Actually Stored

productSchema.virtual("priceAfterDiscount").get(function() {
  return this.price - (this.price * this.discount / 100);
});

// Or a virtual that pulls data from another collection (reverse population)
productSchema.virtual("reviews", {
  ref: "Review",
  foreignField: "product",
  localField: "_id"
});
Important: a virtual is never stored in the database — it's calculated only when accessed. You must enable toJSON: { virtuals: true } for it to show up in responses.
ConceptUse It When...
Instance MethodsYou need an operation tied to a specific document (e.g., comparePassword)
Static MethodsYou need a custom query that repeats often (e.g., findActiveUsers)
VirtualsYou need a computed field that shouldn't be stored (e.g., fullName, priceAfterDiscount)

Section Four

Middleware (Hooks) — Pre and Post

Middleware functions run automatically before or after a given operation (save, find, remove, etc.).

TypeWhen It Runs
preBefore the operation
postAfter the operation

Example 1 — pre("save"): Hashing the Password Before Saving

const bcrypt = require("bcryptjs");

userSchema.pre("save", async function(next) {
  if (!this.isModified("password")) return next();  // skip re-hashing if password wasn't changed
  this.password = await bcrypt.hash(this.password, 12);
  next();
});
A common beginner question: why this.isModified("password")? Because if you call save() to update a different field (like the name), this check prevents the password from being re-hashed every single time you save, even though it's already hashed from before.

Example 2 — pre("find"): Hiding Soft-Deleted Products

productSchema.pre(/^find/, function(next) {
  this.find({ isDeleted: { $ne: true } });
  next();
});

/^find/ is a regex that covers every operation starting with "find" (find, findOne, findById, etc.) at once.

Example 3 — post("save"): Logging or Sending an Email

orderSchema.post("save", function(doc) {
  console.log(`Order ${doc._id} was created`);
  // could send a confirmation email here, for example
});

Example 4 — pre("findOneAndDelete"): Cascade Delete

// If a Category is deleted, delete all products linked to it
categorySchema.pre("findOneAndDelete", async function(next) {
  const categoryId = this.getQuery()._id;
  await Product.deleteMany({ category: categoryId });
  next();
});

Section Five

The "this" Context Trap in Middleware

A point that confuses many beginners: what this refers to changes depending on the middleware type.

// In document middleware (save, validate) — "this" refers to the Document
userSchema.pre("save", function(next) {
  console.log(this.name);  // ✅ works
  next();
});

// In query middleware (find, findOne, updateOne) — "this" refers to the Query itself, not a Document
productSchema.pre("find", function(next) {
  console.log(this.getQuery());  // ✅ works — returns the search condition
  console.log(this.name);        // ❌ undefined — there's no document yet
  next();
});
Tip
  • Never use arrow functions for middleware callbacks — arrow functions don't bind their own this, so it will point to the surrounding scope instead of the document/query.
  • When debugging middleware behavior, log this.constructor.modelName to confirm which model context you're actually inside.

Section Six

Population — Replacing Manual Joins

The Core Idea

Once you define a ref in the schema, you can replace an ObjectId with the full referenced document at query time.

const orderSchema = new mongoose.Schema({
  user: { type: mongoose.Schema.Types.ObjectId, ref: "User" },
  products: [{ type: mongoose.Schema.Types.ObjectId, ref: "Product" }]
});
// Without populate
const order = await Order.findById(id);
console.log(order.user);  // just the ObjectId

// With populate
const order = await Order.findById(id).populate("user");
console.log(order.user);  // the full User document

Populate with Field Selection (Like Projection)

const order = await Order.findById(id).populate("user", "name email");
// only fetches name and email from User, not everything

Multiple Populates Together

const order = await Order.findById(id)
  .populate("user", "name email")
  .populate("products", "title price");

Nested Population — When a Reference Itself Has Another Reference

const review = await Review.findById(id).populate({
  path: "product",
  populate: {
    path: "category",
    select: "name"
  }
});

Populate with Filter and Sort

const category = await Category.findById(id).populate({
  path: "products",
  match: { price: { $gte: 100 } },
  select: "title price",
  options: { sort: { price: -1 }, limit: 5 }
});

Section Seven

The N+1 Query Problem & When to Avoid Populate

Populate performs a separate additional query for each reference — it's not a true JOIN like in SQL. If you have an array of 100 orders and each one is populated, this can result in hundreds of queries.

The N+1 problem: one query to get the list, then N additional queries (one per referenced document) to populate each one — performance degrades quickly as the list grows.

The Better Alternative for High Performance

Use the Aggregation Pipeline with $lookup instead of Populate, especially with large datasets or a high query volume.

// Instead of Populate, you can use:
Order.aggregate([
  { $match: { _id: orderId } },
  { $lookup: { from: "users", localField: "user", foreignField: "_id", as: "user" } }
])
Tips & Tricks
  • Populate is fine for typical CRUD endpoints with reasonable list sizes and pagination — don't over-optimize prematurely.
  • Reach for $lookup-based aggregation when a single request would otherwise trigger dozens or hundreds of populate queries, or when you need to combine population with grouping/filtering logic in the same query.
  • Always paginate lists that use populate — an unbounded list with nested populate is a common source of slow endpoints in production.

Section Eight

Mongoose Validation vs. MongoDB Schema Validation

const userSchema = new mongoose.Schema({
  email: {
    type: String,
    required: [true, "Email is required"],
    unique: true,
    lowercase: true,
    validate: {
      validator: function(value) {
        return /^\S+@\S+\.\S+$/.test(value);
      },
      message: "Invalid email format"
    }
  },
  age: {
    type: Number,
    min: [18, "Must be at least 18 years old"],
    max: [100, "Age cannot exceed 100"]
  }
});
The difference from MongoDB's own $jsonSchema validation: Mongoose validation runs at the application layer (Node.js), before the data even reaches the database. It responds to the user faster, but doesn't protect you if someone accesses the database directly, bypassing your application entirely.

Section Nine

Custom Error Messages with Enum

const orderSchema = new mongoose.Schema({
  status: {
    type: String,
    enum: {
      values: ["pending", "confirmed", "shipped", "delivered"],
      message: "{VALUE} is not a valid status"
    },
    default: "pending"
  }
});

The {VALUE} placeholder is automatically replaced with the actual invalid value submitted, producing a clear, specific error message.

Section Ten

Indexes in Mongoose

userSchema.index({ email: 1 }, { unique: true });
productSchema.index({ category: 1, price: -1 });

These map directly to the same index concepts covered earlier at the MongoDB shell level — Mongoose simply lets you declare them alongside the schema definition itself, keeping index intent version-controlled with your model code.

Tip
  • Mongoose builds indexes automatically when the app starts (in development), which can be slow on large collections — in production, create indexes explicitly via migration scripts or the shell instead of relying on auto-indexing.
