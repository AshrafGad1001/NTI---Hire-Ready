Topic One

SQL vs. NoSQL

SQL (Relational Databases)

Examples: SQL Server, MySQL, PostgreSQL.

  • Structured — data lives in tables with a fixed, predefined schema (columns and types).
  • Relations — tables are linked via Foreign Keys.
  • ACID compliant — very high accuracy in transactions (critical for banking, e-commerce transactions).
  • Vertical Scaling — scale by upgrading a single server (RAM/CPU).
  • A unified query language (SQL) across implementations.

NoSQL (Non-Relational Databases)

Example: MongoDB.

  • Unstructured / Flexible Schema — each document in a collection can have a different shape.
  • No fixed relations — instead of JOINs, data uses Embedding or Referencing.
  • BASE model instead of ACID: Basically Available, Soft state, Eventually consistent — faster, less strict on immediate consistency.
  • Horizontal Scaling — add more servers (Sharding), easier to scale with massive data volumes.
  • Multiple types exist: Document (MongoDB), Key-Value (Redis), Column-family (Cassandra), Graph (Neo4j).

When to Use Which

ScenarioBetter Fit
Complex, stable relationships (financial transactions)SQL
Frequently changing data shape, fast development needsNoSQL
Massive scale (millions of users)Usually NoSQL
Complex reports requiring many joinsSQL

Topic Two

ACID vs. BASE

ACID (SQL Model)

Philosophy: accuracy and consistency come first, even at the cost of speed.

LetterMeaningExplanation
AtomicityAll-or-nothingA transaction either completes fully or is fully rolled back — no partial state.
ConsistencyValid state transitionsData moves from one valid state to another; no rule/constraint violations.
IsolationConcurrent safetyConcurrent transactions behave as though each runs alone, with no interference.
DurabilityPermanenceOnce committed, data is guaranteed to persist even after a crash.

Example: transferring money between two bank accounts — ACID is mandatory, since a partial transfer (money leaving one account but never arriving at the other) is unacceptable.

BASE (NoSQL Model)

Philosophy: prioritize availability and speed, accepting that data may take a moment to fully synchronize.

LetterMeaningExplanation
Basically AvailableAlways respondsThe system responds to every request, even if part of it is degraded.
Soft stateNot fixedData state can change over time even without new input, due to replica synchronization.
Eventually consistentConverges over timeReplicas aren't instantly identical, but will converge within a short time.

Example: a Like count on a social media post — a brief delay in updating the number across viewers is harmless. Speed matters more than instant accuracy.

MongoDB in Practice

MongoDB supports multi-document transactions since version 4.0, giving a choice: use ACID transactions when accuracy is essential, or rely on eventual consistency when speed matters more.

const session = await mongoose.startSession();
session.startTransaction();
try {
  await Order.create([orderData], { session });
  await Product.updateMany(..., { session });
  await session.commitTransaction();
} catch (err) {
  await session.abortTransaction();
}

Topic Three

The CAP Theorem

In any distributed database, a system cannot simultaneously guarantee all three of the following once a network issue occurs — it can guarantee at most two.

The Three Properties

  • Consistency (C) — every node returns the exact same data at the same moment.
  • Availability (A) — every request receives a response (success or failure), even if it isn't the newest data.
  • Partition Tolerance (P) — the system keeps functioning even if nodes lose the ability to communicate with each other.

Why Not All Three?

Network partitions are inevitable in distributed systems. So the real trade-off during a partition is between Consistency and Availability — Partition Tolerance isn't optional, since network failures will happen regardless.

  • Choosing Consistency — some nodes must stop responding (reject requests) until data is synchronized, to avoid returning incorrect data.
  • Choosing Availability — requests are served from every node, but data may briefly differ between nodes (not fully consistent).

Real-World Examples

SystemChoiceWhy
MongoDB (default)CPPrefers to pause writes on the primary rather than risk inconsistency across replicas.
CassandraAPPrefers to always respond, even with slightly stale data, then reconciles eventually.

Read/Write Concerns in MongoDB

// Write Concern - confirms the write reached a certain number of nodes
db.orders.insertOne(order, { writeConcern: { w: "majority" } })

// Read Concern - ensures reads come from a synchronized copy
db.orders.find().readConcern("majority")

Using w: "majority" sacrifices a bit of speed to guarantee higher consistency — CAP trade-offs are configuration decisions you make directly in your project.

Topic Four

NoSQL Database Types

1. Key-Value Store

The simplest type — every entry is a unique key mapped to a value (string, number, JSON, binary). Like a distributed HashMap/Dictionary.

Examples: Redis, Riak. Use cases: caching, session storage, real-time leaderboards, temporary shopping carts.

2. Wide Column Store

Similar to tables, but each row can have different columns from the next. Data is stored column-by-column rather than row-by-row, making it very fast for reading specific columns across millions of rows.

Examples: Apache HBase, Cassandra. Use cases: Big Data analytics, time-series data (IoT sensors, logs), systems requiring massive high-speed writes.

3. Document Store

Data is stored as documents (typically JSON/BSON), each with a flexible structure.

Examples: MongoDB, CouchDB. Use cases: general web/mobile applications, variable-shaped content (CMS, catalogs) — the most common NoSQL type in MERN-stack projects.

4. Graph Store

Data is represented as Nodes (entities) and Edges (relationships), designed specifically to query complex relationships quickly — something SQL and MongoDB struggle with.

Examples: Neo4j, InfiniteGraph. Use cases: social networks (friend recommendations), recommendation engines, fraud detection, knowledge graphs.

Quick Comparison

TypeStrongest AtWeakest At
Key-ValueLookup by keyComplex queries
Wide ColumnReading/writing single columns at massive scaleComplex relationships
DocumentFlexibility + medium-complexity queriesMany joins between collections
GraphRelationships and traversalSimple flat data at huge scale

Topic Five

BSON (Binary JSON)

BSON stands for Binary JSON — the format MongoDB actually uses to store documents on disk, not plain JSON.

Why Not Plain JSON?

Problem with JSONBSON's Solution
No precise data types (every number is just "number")Specific types: Int32, Int64, Double, Decimal128
No dedicated date typeNative Date type stored directly as binary
No binary data type (images, files)Native Binary Data type
Slow parsing (must be read as text first)Faster traversal — field lengths are known upfront without reading the entire string
No ObjectId typeObjectId is a native BSON type (used for MongoDB's _id)

Important Note

The JSON you see in a response (Postman, frontend, etc.) is a textual representation automatically converted from BSON. BSON itself is stored as binary inside MongoDB's .wt files (WiredTiger storage engine).

The 16MB Document Limit

This is a direct consequence of BSON's design: it uses an Int32 to store document size, capping the maximum possible size at 16MB. This is why arrays that can grow unbounded (e.g., a huge number of comments) should use Referencing instead of Embedding.

Topic Six

Embedding vs. Referencing

The most important design decision in MongoDB schema design.

Embedding

Nesting related data directly inside the parent document.

{
  name: "Ashraf",
  addresses: [
    { city: "Shebin El-Kom", street: "..." }
  ]
}

Use it when the relationship is "one-to-few" and the data is almost always read together.

Referencing

Similar to a Foreign Key — storing a reference (ID) to another document instead of embedding it.

{
  name: "Ashraf",
  projectId: ObjectId("...")
}

Use it when the relationship is "one-to-many" at scale, or the data changes frequently, or it's shared across multiple parents.

Golden Rule: if an array can grow without bound (e.g., comments on a viral post), never embed it — MongoDB documents are capped at 16MB.

db.posts.find({ $or: [{ likes: { $gt: 500 } }, { category: "Trending" }] })

Topic Nine

The Aggregation Pipeline

Core Stages

// $match — filtering, like WHERE
{ $match: { status: "completed", totalPrice: { $gte: 100 } } }

// $group — grouping, like GROUP BY
{ $group: {
    _id: "$userId",
    totalSpent: { $sum: "$totalPrice" },
    orderCount: { $sum: 1 },
    avgOrder: { $avg: "$totalPrice" }
}}

// $sort / $limit / $skip
{ $sort: { price: -1 } }
{ $skip: 10 }
{ $limit: 5 }

// $project — reshaping fields, like SELECT
{ $project: { title: 1, price: 1, priceAfterTax: { $multiply: ["$price", 1.14] }, _id: 0 } }

// $lookup — join across collections
{ $lookup: { from: "products", localField: "productId", foreignField: "_id", as: "productDetails" } }

// $unwind — flatten an array into separate documents
{ $unwind: "$items" }

// $addFields — add computed fields without removing existing ones
{ $addFields: { finalPrice: { $subtract: ["$price", "$discount"] } } }

// $count
{ $count: "totalElectronics" }

Advanced Stages

// $facet — run multiple sub-pipelines at once (useful for dashboards)
{ $facet: {
    priceStats: [{ $group: { _id: null, avgPrice: { $avg: "$price" } } }],
    categoryCounts: [{ $group: { _id: "$category", count: { $sum: 1 } } }]
}}

// $bucket — group data into ranges
{ $bucket: { groupBy: "$price", boundaries: [0, 100, 500, 1000], default: "Other" } }

// $replaceRoot — reshape the root document
{ $replaceRoot: { newRoot: "$items" } }

// $out / $merge — write pipeline results to a collection
{ $merge: { into: "userTotals", whenMatched: "merge" } }

// $sample — random documents
{ $sample: { size: 3 } }

db.products.find()
  .sort({ createdAt: -1 })

Topic Eleven

find() vs. findOne()

find()

Returns a cursor pointing to every document matching the filter — could be zero, one, or millions of documents.

db.products.find({ category: "Electronics" })
  • Returns an array-like cursor, not a plain array.
  • Supports chaining .sort(), .limit(), .skip().
  • Returns an empty cursor (not null) if nothing matches.

findOne()

Returns only the first matching document, even if multiple documents match.

db.products.findOne({ category: "Electronics" })
  • Returns a single object directly (not an array, not a cursor).
  • Returns null if no match is found.

When to Use Which

ScenarioUse
Need a full list (e.g., all products in a category)find()
Check if a document exists (e.g., email lookup at signup)findOne()
Fetch a user by a unique field (_id, email)findOne() / findById()
Pagination / paged listingsfind()
Mongoose adds findById() as shorthand for findOne({ _id: id }).

Topic Twelve

Projection

The second parameter of find(), used to control which fields are returned instead of the entire document.

db.Posts.find(
  { Sticker: { $nin: ["Happy Bear", "Angry Bear"] } },
  { UID: 1, Comments: 1 }
)

Inclusion (value: 1)

Specify only the fields you want; everything else is excluded automatically.

db.Posts.find({}, { UID: 1, Comments: 1 })

Exclusion (value: 0)

Specify fields to exclude; everything else is returned.

db.Posts.find({}, { Sticker: 0 })

Excluding _id

db.Posts.find({}, { UID: 1, Comments: 1, _id: 0 })
Important rule: you cannot mix inclusion and exclusion in the same query, except for _id, which is always allowed as an exception.

Practical Example

db.products.find(
  { category: "Electronics" },
  { title: 1, price: 1, imageCover: 1, ratingsAverage: 1 }
)

Reduces the amount of data transferred over the network and speeds up response time, especially with large datasets.

Topic Thirteen

Index Properties

1. Unique

Prevents duplicate values in a field across all documents.

db.users.createIndex({ email: 1 }, { unique: true })

Use case: email or username fields in an auth system, to prevent duplicate account registration.

2. Sparse

The index ignores documents where the field is missing entirely, instead of indexing them as null.

db.users.createIndex({ phoneNumber: 1 }, { sparse: true })

Use case: optional fields (e.g., not every user provides a phone number). Combining sparse with unique avoids conflicts that would otherwise occur when many documents share a null value.

3. Partial

Similar to sparse but more precise — lets you define a custom filter expression, so the index only covers documents matching that condition.

db.orders.createIndex(
  { customerId: 1 },
  { partialFilterExpression: { status: "completed" } }
)

Use case: indexing only completed orders instead of all orders, reducing index size and speeding up frequently filtered queries.

4. Compound

A single index built from more than one field.

db.products.createIndex({ category: 1, price: -1 })

Use case: filtering products by category while sorting by price simultaneously — much faster than two separate indexes.

The ESR Rule (Equality, Sort, Range) determines the best field order inside a compound index: equality fields first, then sort fields, then range fields.

Topic Fourteen

Indexing — Pros & Cons

Pros

BenefitExplanation
Read performanceInstead of a full collection scan, the index jumps directly to the right location.
Faster sortingIf an index exists on the sort field, MongoDB can use the index's existing order instead of sorting all data at query time.
Improved aggregationEarly $match/$sort stages benefit from indexes, reducing documents processed in later stages.
Enforcing data rules (unique)A unique index prevents duplicate values (e.g., email) without extra application-level validation.
Reduced memory pressureIndex lookups load only a small portion of data into memory compared to scanning the full collection.

Cons

DrawbackExplanation
Slower writesEvery insert, update, or delete must update all related indexes — more indexes mean slower writes.
Extra storage usageEach index takes up disk space separate from the actual data.
RAM consumptionMongoDB tries to keep active indexes in memory; if indexes exceed available RAM, disk I/O slows things down instead of helping.
Maintenance complexityRequires ongoing monitoring to identify and remove unused indexes.
Hard limit on countMongoDB allows a maximum of 64 indexes per collection.
Misuse can hurt performanceA poorly chosen index (rarely filtered field, wrong field order in a compound index) wastes space and resources with little benefit.

Golden Rule

Do index: fields frequently used in find()/$match conditions, sort(), and foreign-key-like references.

Don't index: rarely filtered/sorted fields, or fields that change value extremely frequently (e.g., counters updated every second), since the write overhead outweighs the benefit.

Practical Example

db.products.createIndex({ category: 1, price: -1 })  // frequently filtered and sorted
db.reviews.createIndex({ productId: 1 })              // foreign-key-like, used in $lookup

Topic One

SQL Mindset vs. NoSQL Mindset

SQL: Think "Normalization" First

The philosophy: split data into the smallest possible units, avoid any duplication, and link everything with Foreign Keys. This decision is made while designing the tables — often before you even know which queries will run against them.

-- SQL: three separate tables, linked by Foreign Keys
Users (id, name, email)
Orders (id, user_id, date)
OrderItems (id, order_id, product_id, quantity)

Whenever a query needs combined data, you run a JOIN at query time.

NoSQL: Think "Query Patterns" First

The philosophy: design the schema around how you'll read the data, not around how "clean" it looks in theory. The question isn't "what's the correct relationship between the data?" — it's "what query will run most often, and how do I make it fast?"

// NoSQL: order data and its related product info are grouped together
{
  _id: 1,
  user: { name: "Ashraf", email: "..." },  // Embedded
  date: "...",
  items: [
    { productName: "Laptop", quantity: 1, price: 15000 }
  ]
}

No JOIN needed at read time — everything is already available in a single document.

The Core Difference

SQLNoSQL
Starting pointRelationships between entitiesActual queries that will run (access patterns)
Primary goalAvoid data duplication (integrity)Read performance
Schema flexibilityFixed, hard to migrateFlexible — add fields to any document independently
Decision timingTables designed first, queries come laterQueries must be known first, then the schema is designed
Most common mistake: bringing the full SQL mindset into NoSQL — referencing everything like Foreign Keys and joining ($lookup) on every query. The result is poor performance, because you lose NoSQL's biggest advantage: keeping related data together from the start.
Tip
  • Golden rule: "Data that is accessed together should be stored together."
  • Before writing a single line of schema code, write down the top 5–10 queries your app will actually run.
  • If you find yourself justifying a schema decision with "because that's how it'd work in SQL," stop and re-check against your access patterns.

Topic Two

Design Pattern 1 — Embedding

The idea: place related data directly inside the same document, instead of a separate collection.

{
  _id: 1,
  name: "Ashraf",
  addresses: [
    { city: "Shebin El-Kom", street: "Main St", isDefault: true },
    { city: "Cairo", street: "Nasr City", isDefault: false }
  ]
}

When to Use It

  • The relationship is one-to-few (e.g., a user has 2–3 addresses, not thousands).
  • The related data is almost always read together (there's no scenario where you fetch the user without their addresses).
  • The data doesn't change frequently or independently of the parent.

Pros

  • A single query retrieves everything (no $lookup needed).
  • Excellent read performance.
  • Atomic updates — parent and embedded data update together in one operation.

Cons

  • If the array grows too large, the document size grows with it (risking the 16MB limit).
  • If the embedded data is shared across multiple parents, duplication occurs.
Tips & Tricks
  • A good rule of thumb: embed when the array size is bounded and predictable (rarely exceeds a few dozen items).
  • If you're unsure whether to embed, ask: "Will I ever need this child data without its parent?" If no — embed.
  • Embedding read-only "snapshot" data (e.g., a price at time of purchase) is safe even if the source can change later — see the Computed/Snapshot note in the Common Mistakes section.

Topic Three

Design Pattern 2 — Referencing

The idea: store just a reference (ID) instead of the full data, similar to a Foreign Key.

// in users
{ _id: 1, name: "Ashraf" }

// in projects
{ _id: 101, title: "GoRent", ownerId: 1 }

When to Use It

  • The relationship is a large one-to-many or many-to-many.
  • The related data changes frequently and independently of the other side.
  • The related data is shared across multiple documents (e.g., one product referenced by many orders).
  • The array could grow without bound (e.g., a very large number of comments).

Pros

  • Documents stay small and organized.
  • Updating shared data (e.g., a user's profile) only requires updating one place.
  • No data duplication.

Cons

  • Requires a $lookup (like a JOIN) at read time — slower than embedding.
  • Not atomic — updating two related documents together requires a transaction.
Tips & Tricks
  • Always index the field you're referencing by (e.g., ownerId), since it's effectively your "foreign key lookup" field.
  • If you find yourself doing $lookup on the same field in almost every query, consider whether a Subset or Computed pattern could reduce that need.
  • Two-way referencing (both sides store each other's IDs) is fine for many-to-many, as long as you pick a clear "primary" side to update first in your application logic.

Topic Four

Design Pattern 3 — Subset Pattern

The idea: instead of fully embedding or fully referencing, use a middle ground — store only a small portion of the related data (e.g., the most recent/most relevant items), while the full data lives in a separate collection with a reference.

// Product document holds only the latest 5 reviews, not all of them
{
  _id: 1,
  title: "Laptop HP",
  price: 15000,
  recentReviews: [   // Subset only — latest 5
    { user: "Sara", rating: 5, comment: "Great!" },
    { user: "Omar", rating: 4, comment: "Good" }
  ],
  totalReviewsCount: 230  // pre-computed total
}

// The full set of reviews lives in a separate collection
db.reviews.find({ productId: 1 })

When to Use It

When you have a large amount of related data (like reviews), but you also need a small portion of it to appear instantly alongside the parent (e.g., showing the latest 3 ratings on a product page without an extra query).

Practical example: in an e-commerce API, this is the ideal solution for displaying "latest 3 reviews" on a product page without running an aggregation on every page load.
Tips & Tricks
  • Keep the subset small and purpose-built (e.g., "latest 3–5 items") — it's a display optimization, not a full copy.
  • Update the subset only when new data is added to the full collection (e.g., a background job or an application-level trigger), not on every read.
  • Combine this pattern with the Computed Pattern: store both a small subset (recentReviews) and a pre-calculated aggregate (averageRating) side by side.

Topic Five

Design Pattern 4 — Bucket Pattern

The idea: instead of creating a separate document for every single reading/event, group a batch of readings from the same time window into one document — commonly used with time-series data.

// Instead of one document per second (thousands of documents)
// group all readings for one hour into a single document
{
  sensorId: "sensor_001",
  date: "2026-07-12",
  hour: 14,
  readings: [
    { minute: 0, temp: 25.3 },
    { minute: 1, temp: 25.5 },
    { minute: 2, temp: 25.4 }
    // ... rest of the hour's minutes
  ],
  avgTemp: 25.4,
  maxTemp: 26.1,
  minTemp: 24.8
}

When to Use It

  • Time-series data (IoT sensor readings, logs, analytics events).
  • A massive number of closely-spaced-in-time readings.

Pros

  • Dramatically reduces the total number of documents (thousands instead of millions).
  • Indexes stay smaller and faster.
  • Easy to pre-compute aggregates (avg, max, min) and store them inside the bucket itself.
Tips & Tricks
  • Pick a bucket window (hour, day) based on your query patterns — how granular do reads actually need to be?
  • MongoDB's native Time Series Collections (available since v5.0) automate much of this pattern — worth checking if your MongoDB version supports it before hand-rolling buckets.
  • Watch out for buckets that grow unbounded within the time window if the event rate spikes unexpectedly.

Topic Six

Design Pattern 5 — Computed Pattern

The idea: instead of recalculating a value every time it's requested (e.g., averaging all reviews on every page load), calculate it once and store it as a ready-made field, updating it only when the underlying data changes.

// Instead of running an aggregation every time the product page loads
{
  _id: 1,
  title: "Laptop HP",
  price: 15000,
  averageRating: 4.5,     // pre-computed
  totalReviews: 230       // pre-computed
}

// When a new review is added, only these two fields get updated —
// not recalculated from all 230 reviews on every page view

When to Use It

  • A calculation is read very frequently (every time a product page opens) but changes relatively rarely (a new review every so often).
  • You want to avoid an expensive aggregation (e.g., averaging across thousands of documents) on every request.
Practical example: in an e-commerce API, instead of running the aggregation pipeline that computes avgRating every time a product page loads, store the result directly on the Product document and update it only when a review is added or removed.
Tips & Tricks
  • Update computed fields via application logic right after the write that changes them (e.g., inside the same request that creates a review), not through a separate cron job unless near-real-time accuracy isn't required.
  • For high write volume, consider using MongoDB transactions to keep the computed field and the source data consistent.
  • This pattern trades a small amount of write complexity for a large gain in read performance — worth it wherever reads vastly outnumber writes.

Topic Seven

Relationship Types

One-to-One

One entity is linked to exactly one entity of another type.

// A user and their detailed profile info (rarely read together)
{ _id: 1, name: "Ashraf", profileDetails: { bio: "...", cv: "..." } }

Decision: usually embed, unless the data is very large or rarely read alongside the parent.

One-to-Few

One entity is linked to a small number (2–100) of entities of another type.

// A user and their addresses (2–3 addresses)

Decision: Embed — the count is small and stable.

One-to-Many

One entity is linked to a relatively large number (hundreds to thousands) of entities of another type.

// A category and its products (could be thousands)

Decision: Reference, usually — the count is large and constantly changing.

One-to-Squillions

One entity is linked to a massive (millions) number of entities of another type.

// A single server and its millions of log entries

Decision: Referencing is mandatory — likely combined with the Bucket Pattern to reduce document count.

Many-to-Many

Each entity of one type can be linked to multiple entities of the other type, and vice versa.

// Students and Courses — each student is enrolled in several courses,
// and each course has many students
{ _id: 1, name: "Ashraf", enrolledCourseIds: [101, 102, 103] }
{ _id: 101, title: "React Basics", enrolledStudentIds: [1, 5, 9] }

Decision: usually two-way referencing, or referencing from a single direction based on which direction is queried more often.

Tips & Tricks
  • When in doubt about a relationship's cardinality, estimate the maximum realistic count over the object's lifetime — that number alone often decides between embed and reference.
  • For many-to-many, if one direction is queried far more often than the other, consider referencing only in that direction and using a $lookup for the rare reverse query instead of maintaining both arrays.

The Schema Design Process (Steps 1–4)

Step 1 — Identify the Entities

Write a list of every core "thing" in your system.

Example: User, Product, Order, Review, Category

Step 2 — Identify the Most Common Queries (Access Patterns)

This is the most important step in NoSQL design. Before writing any schema, ask yourself:

  • What query will run most often? (e.g., "get all products in a given category")
  • What actions do users perform frequently? (e.g., "open a product page, view its reviews")
  • What's the read-to-write ratio? Is this workload read-heavy or write-heavy?

Write these queries down explicitly before designing anything:

1. Get all products in a category, sorted by price
2. Get a single product with its latest 5 reviews
3. Get all orders for a specific user
4. Search products by name

Step 3 — Identify the Relationships Between Entities

For each pair of entities, determine the type (one-to-one, one-to-few, one-to-many, many-to-many).

User → Orders: One-to-Many
Order → Products: Many-to-Many
Product → Reviews: One-to-Squillions

Step 4 — Apply the Right Pattern to Each Relationship

Ask three questions for every relationship:

  1. Growth rate — is the count small and stable, or large and increasing?
  2. Update frequency — does the data change often, or rarely?
  3. Read-together frequency — is the child data needed every time the parent is fetched?

Based on the answers, choose: Embed / Reference / Subset / Bucket / Computed.

Tips & Tricks
  • Keep your access-pattern list as a living document — revisit it whenever a new feature changes how data is queried.
  • It's fine to mix patterns within the same schema — e.g., embed addresses, reference orders, and use a computed field for ratings, all in the same User/Product design.
  • When two access patterns conflict (one favors embedding, another favors referencing), prioritize whichever query runs more frequently or is more performance-critical for the user experience.

Topic Nine

Step 5 — Avoiding Common Mistakes

This isn't a "design" step — it's a review and critique step. After designing a schema, go back and check it against these common pitfalls.

Mistake 1 — Unbounded Arrays

// ❌ Very common mistake
{
  productId: 1,
  reviews: [ /* thousands of reviews embedded directly in the product */ ]
}

Problem: this will eventually hit the 16MB limit, and the document becomes slow to read and write well before that limit is even reached.

Fix: use Referencing or the Subset Pattern instead.

Mistake 2 — Deeply Nested Documents

// ❌ Common mistake
{
  user: {
    profile: {
      settings: {
        preferences: {
          notifications: {
            email: { enabled: true }
          }
        }
      }
    }
  }
}

Problem: deeply nested fields are hard to update, and queries become unwieldy (user.profile.settings.preferences.notifications.email.enabled).

Fix: try to keep nesting to 2–3 levels at most.

Mistake 3 — Over-Embedding to "Avoid SQL-Style Joins"

This is the most dangerous mistake — beginners often feel that every embed is a "performance win," so they embed everything even when it doesn't make sense.

// ❌ Mistake — embedding data that changes constantly and is shared across many documents
{
  orderId: 1,
  productDetails: { name: "Laptop", price: 15000, stock: 45 }  // full copy of product data
}

Problem: if the product's price changes, you'd need to update every past order containing that product — a disaster.

Fix: the order should store only a snapshot of relevant data at the moment of purchase (e.g., the price at sale time), not a live copy that's expected to stay in sync with changes.

Key distinction: embedding a snapshot (immutable, point-in-time data) is safe and often correct. Embedding a live copy of mutable data that's also stored elsewhere is the actual mistake.
Tips & Tricks
  • Before finalizing any schema, explicitly write "is this field a snapshot or a live copy?" next to every embedded object that duplicates data from elsewhere.
  • Run db.collection.find(...).explain("executionStats") against your top access-pattern queries to catch accidental COLLSCANs early.
  • Periodically check actual document sizes in production (db.collection.stats()) — unbounded arrays often creep up slowly before becoming a real problem.

Step 6 — Auditing a Real Project

This is a real, practical application step — not a hypothetical exercise. Take an actual schema from a live project you've built (e.g., GoRent or an e-commerce API) and run a full audit on it.

How to Run the Audit

  1. Open every schema you have (Product, Order, Review, etc.).
  2. For each one, ask: "Why did I choose to embed here? Why did I choose to reference there?" If the honest answer is "I'm not sure, it just felt easier at the time," that decision was made without real analysis.

  • Turn the audit into a recurring habit — revisit schemas every few months as usage patterns evolve, not just once at project launch.

  • Document each schema decision with a one-line comment in code (e.g., // embedded: 1-to-few, always read together) so future-you (or teammates) understand the reasoning without re-deriving it.

Section One

The Core Idea

Since NoSQL databases are flexible by nature, that flexibility is both a strength and a risk — anyone can insert a document in almost any shape, even one missing essential fields or containing the wrong data types. Schema Validation is MongoDB's built-in mechanism for enforcing rules at the collection level, without fully sacrificing NoSQL's flexibility.

Rules are attached to a collection, and any document being inserted or updated must comply with them, or MongoDB rejects the operation.

db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "email", "age"],
      properties: {
        name: {
          bsonType: "string",
          description: "must be a string and is required"
        },
        email: {
          bsonType: "string",
          pattern: "^.+@.+$",
          description: "must be a valid email format"
        },
        age: {
          bsonType: "int",
          minimum: 18,
          maximum: 100,
          description: "must be an integer between 18 and 100"
        }
      }
    }
  }
})

Attempting this insert:

db.users.insertOne({ name: "Ashraf", age: 15 })

...would be rejected for two reasons: email is missing (required), and age is below the minimum (18).

Tip
  • Validation is enforced at the database engine level — it applies regardless of which application, script, or admin tool is writing the data.
  • You can add validation to a brand-new collection (via createCollection) or retrofit it onto an existing one (via collMod), covered in Section Five.

Adding Validation to an Existing Collection

If the collection already exists and you need to add rules to it:

  collMod: "users",

    $jsonSchema: {

  validationLevel: "moderate"
})

This is the safer path for production collections that already contain live data — combining collMod with validationLevel: "moderate" avoids suddenly breaking writes to older, non-compliant documents.

Section Ten

Important Notes & Limitations

  • Not a replacement for backend validation (e.g., Mongoose schemas or Joi) — it's an additional layer of protection at the database level, not a substitute. If someone accesses the database directly (an admin, a script, a migration), database-level validation still protects data integrity even if the backend was bypassed.
  • Performance — validation adds a small overhead to every insert/update, but this is usually negligible compared to the benefit of guaranteed data integrity.
  • Not meant for complex business logic — rules like "this product can only be sold if there's an active promotional offer" are application logic, not something that belongs in schema validation.
  • Schema evolution — as your application changes, remember to update the validator too; a forgotten stale validator can silently block legitimate new fields.
  • No cross-document rules — $jsonSchema validates a document against itself; it cannot enforce rules that depend on data in other documents or collections (e.g., "this email must be unique across the whole collection" — that still requires a unique index).
Tips & Tricks
  • Combine schema validation with a unique index where needed — validation checks shape and type, indexes enforce uniqueness across documents.
  • Keep a copy of every collection's validator schema in your project's codebase (e.g., a /schemas folder) so it's version-controlled alongside your Mongoose models, not just living invisibly inside the database.
  • When adding a new required field to a schema that already has production data, always roll out with moderate + warn first — treat it the same as a database migration, not a simple config change.

Middleware (Hooks) — Pre and Post

Middleware functions run automatically before or after a given operation (save, find, remove, etc.).

TypeWhen It Runs
preBefore the operation
postAfter the operation

Example 1 — pre("save"): Hashing the Password Before Saving

const bcrypt = require("bcryptjs");

userSchema.pre("save", async function(next) {
  if (!this.isModified("password")) return next();  // skip re-hashing if password wasn't changed
  this.password = await bcrypt.hash(this.password, 12);
  next();
});
A common beginner question: why this.isModified("password")? Because if you call save() to update a different field (like the name), this check prevents the password from being re-hashed every single time you save, even though it's already hashed from before.

Example 2 — pre("find"): Hiding Soft-Deleted Products

productSchema.pre(/^find/, function(next) {
  this.find({ isDeleted: { $ne: true } });
  next();
});

/^find/ is a regex that covers every operation starting with "find" (find, findOne, findById, etc.) at once.

Example 3 — post("save"): Logging or Sending an Email

orderSchema.post("save", function(doc) {
  console.log(`Order ${doc._id} was created`);
  // could send a confirmation email here, for example
});

Example 4 — pre("findOneAndDelete"): Cascade Delete

// If a Category is deleted, delete all products linked to it
categorySchema.pre("findOneAndDelete", async function(next) {
  const categoryId = this.getQuery()._id;
  await Product.deleteMany({ category: categoryId });
  next();
});

Section Five

The "this" Context Trap in Middleware

A point that confuses many beginners: what this refers to changes depending on the middleware type.

// In document middleware (save, validate) — "this" refers to the Document
userSchema.pre("save", function(next) {
  console.log(this.name);  // ✅ works
  next();
});

// In query middleware (find, findOne, updateOne) — "this" refers to the Query itself, not a Document
productSchema.pre("find", function(next) {
  console.log(this.getQuery());  // ✅ works — returns the search condition
  console.log(this.name);        // ❌ undefined — there's no document yet
  next();
});
Tip
  • Never use arrow functions for middleware callbacks — arrow functions don't bind their own this, so it will point to the surrounding scope instead of the document/query.
  • When debugging middleware behavior, log this.constructor.modelName to confirm which model context you're actually inside.

Population — Replacing Manual Joins

The Core Idea

Once you define a ref in the schema, you can replace an ObjectId with the full referenced document at query time.

const orderSchema = new mongoose.Schema({
  user: { type: mongoose.Schema.Types.ObjectId, ref: "User" },
  products: [{ type: mongoose.Schema.Types.ObjectId, ref: "Product" }]
});
// Without populate
const order = await Order.findById(id);
console.log(order.user);  // just the ObjectId

// With populate
const order = await Order.findById(id).populate("user");
console.log(order.user);  // the full User document

Populate with Field Selection (Like Projection)

const order = await Order.findById(id).populate("user", "name email");
// only fetches name and email from User, not everything

Multiple Populates Together

const order = await Order.findById(id)
  .populate("user", "name email")
  .populate("products", "title price");

Nested Population — When a Reference Itself Has Another Reference

const review = await Review.findById(id).populate({
  path: "product",
  populate: {
    path: "category",
    select: "name"
  }
});

Populate with Filter and Sort

const category = await Category.findById(id).populate({
  path: "products",
  match: { price: { $gte: 100 } },
  select: "title price",
  options: { sort: { price: -1 }, limit: 5 }
});

Section Six — Population

Section Seven

The N+1 Query Problem & When to Avoid Populate

Populate performs a separate additional query for each reference — it's not a true JOIN like in SQL. If you have an array of 100 orders and each one is populated, this can result in hundreds of queries.

The N+1 problem: one query to get the list, then N additional queries (one per referenced document) to populate each one — performance degrades quickly as the list grows.

The Better Alternative for High Performance

Use the Aggregation Pipeline with $lookup instead of Populate, especially with large datasets or a high query volume.

// Instead of Populate, you can use:
Order.aggregate([
  { $match: { _id: orderId } },
  { $lookup: { from: "users", localField: "user", foreignField: "_id", as: "user" } }
])
Tips & Tricks
  • Populate is fine for typical CRUD endpoints with reasonable list sizes and pagination — don't over-optimize prematurely.
  • Reach for $lookup-based aggregation when a single request would otherwise trigger dozens or hundreds of populate queries, or when you need to combine population with grouping/filtering logic in the same query.
  • Always paginate lists that use populate — an unbounded list with nested populate is a common source of slow endpoints in production.

Section One

Why Transactions Are Needed

In NoSQL, a single document is inherently atomic — updating one document is guaranteed to happen entirely or not at all. The problem appears when an operation needs to update more than one document across more than one collection at the same time.

The Classic Problem Example

Consider a "purchase a product" operation:

  1. Decrease stock quantity in products
  2. Create a new order in orders
  3. Deduct funds from the user's balance in users
// ❌ Without a transaction — a real risk
await Product.updateOne({ _id: productId }, { $inc: { stock: -1 } });
// The server crashes right here!
await Order.create({ userId, productId, status: "confirmed" });
await User.updateOne({ _id: userId }, { $inc: { balance: -price } });

If the server crashes right after the first step, the result is: stock was decremented, but no order was ever created, and no money was deducted — a product vanished for no reason, and the customer never paid. This is exactly what transactions prevent.

Section One — Why Transactions Are Needed

Section Two

How Transactions Solve the Problem (ACID Guarantee)

A transaction guarantees that all these operations execute as a single unit (all or nothing):

  • If everything succeeds → commit (all changes are persisted together)
  • If anything fails at any step → abort (everything is rolled back, including steps that had already succeeded)
const session = await mongoose.startSession();
session.startTransaction();

try {
  await Product.updateOne(
    { _id: productId },
    { $inc: { stock: -1 } },
    { session }
  );

  await Order.create(
    [{ userId, productId, status: "confirmed" }],
    { session }
  );

  await User.updateOne(
    { _id: userId },
    { $inc: { balance: -price } },
    { session }
  );

  await session.commitTransaction();
  console.log("Transaction succeeded");
} catch (error) {
  await session.abortTransaction();
  console.log("Transaction failed, everything rolled back:", error);
} finally {
  session.endSession();
}
Important: every operation must pass the same session as an option, or it won't be treated as part of the same transaction.

Section Five

Write Conflicts & Retry Logic

If another transaction tries to modify the same document at the same time, MongoDB throws a Write Conflict Error. This is part of the Isolation guarantee in ACID.

try {
  // the operation
} catch (error) {
  if (error.errorLabels && error.errorLabels.includes("TransientTransactionError")) {
    // safe to retry — this error is temporary
  }
  await session.abortTransaction();
}
Best Practice
  • Your code should be prepared to retry when a TransientTransactionError occurs, since it indicates a temporary conflict between transactions, not an actual logic error.
  • MongoDB drivers provide helper wrappers (e.g., withTransaction() in the native driver) that automatically handle retry logic for transient errors — worth using instead of hand-rolling retry loops.

Section Six

Read Concern & Write Concern Inside Transactions

You can control the accuracy-vs-speed trade-off explicitly:

session.startTransaction({
  readConcern: { level: "snapshot" },     // read a fixed snapshot of data as of transaction start
  writeConcern: { w: "majority" }         // writes must be acknowledged by a majority of nodes before success
});

readConcern: "snapshot" matters a lot because it guarantees you're reading the same version of the data throughout the transaction's lifetime, even if someone else modifies the data at the same moment.

Section Seven

When to Use Transactions (and When Not To)

Use Them When:

  • An operation touches more than one collection and all parts must succeed or fail together (like the purchase example above).
  • Financial operations (transferring balance, deducting/adding credit).
  • Operations with a serious race condition risk (e.g., booking the last available ticket or the last item in stock).

Avoid Them When:

  • The operation touches a single document only — MongoDB documents are already atomic, so an extra transaction adds nothing.
  • You have very high throughput (many operations per second) — transactions add noticeable performance overhead.
  • The problem can be solved with a better schema design instead (e.g., embedding) rather than needing coordination across separate collections in the first place.

Section Eight

Real-World Example — Cash Order Checkout

In an e-commerce API, the Cash Order scenario is one of the best real-world fits for a transaction.

const createCashOrder = async (req, res) => {
  const session = await mongoose.startSession();
  session.startTransaction();

  try {
    const cart = await Cart.findById(req.params.cartId).session(session);

    const order = await Order.create(
      [{
        user: req.user._id,
        cartItems: cart.cartItems,
        totalOrderPrice: cart.totalPriceAfterDiscount || cart.totalPrice,
        paymentMethodType: "cash"
      }],
      { session }
    );

    const bulkOptions = cart.cartItems.map((item) => ({
      updateOne: {
        filter: { _id: item.product, quantity: { $gte: item.quantity } },
        update: { $inc: { quantity: -item.quantity, sold: +item.quantity } }
      }
    }));

    const bulkResult = await Product.bulkWrite(bulkOptions, { session });

    // If any product didn't have enough stock, bulkWrite won't update it at all
    if (bulkResult.modifiedCount !== cart.cartItems.length) {
      throw new Error("Insufficient stock for one or more products");
    }

    await Cart.findByIdAndDelete(req.params.cartId).session(session);

    await session.commitTransaction();
    res.status(201).json({ status: "success", data: order });
  } catch (error) {
    await session.abortTransaction();
    res.status(400).json({ status: "fail", message: error.message });
  } finally {
    session.endSession();
  }
};
Why this matters here specifically: if any error occurs after the order was already created (e.g., a stock update failure), without a transaction the customer could end up with a confirmed order while the product was never actually deducted from stock — a genuine data inconsistency.

Section Nine

The Performance Cost of Transactions

Transactions aren't "free" — they take longer than regular operations and hold resources on the server until they're closed (commit/abort). Using them for every simple operation without real need will negatively affect overall system performance.

Golden Rule
  • Only use a transaction when you genuinely need an "all or nothing" guarantee across more than one document/collection — not as a default solution for every update.
  • Keep transactions short-lived: avoid slow operations (like external API calls or heavy computation) inside a transaction block, since long-running transactions hold locks longer and increase the chance of write conflicts with other operations.
  • For single-document updates, rely on MongoDB's built-in document-level atomicity — no transaction wrapper needed.
