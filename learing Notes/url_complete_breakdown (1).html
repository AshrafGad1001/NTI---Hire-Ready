Section One

What Is a URL?

URL = Uniform Resource Locator — the address used to identify the location of a specific resource on the internet and how to reach it.

The key word here is Locator — it tells you where the resource is and how to reach it, not just its name.

Section Two

The Parts of a URL — What Each One Means

Take this full example and break it down piece by piece:

https://www.example.com:8080/products/laptop?category=electronics&sort=price#reviews

1. Scheme (Protocol)

https://

Defines the protocol used to communicate with the server — essentially "how" you'll connect.

  • http — unencrypted
  • https — encrypted (secure), via SSL/TLS
  • ftp — file transfer
  • mailto — opens an email client
  • ws / wss — WebSocket

2. Authority (Made Up of Several Sub-Parts)

a) Userinfo (optional, rarely used today)

username:password@

Historically used to embed login credentials directly in the URL (e.g., FTP). Largely abandoned today for security reasons — the credentials appear in plain sight.

b) Host (Domain)

www.example.com

The server name you're connecting to. Can be either a domain name (as above) or a raw IP address (e.g., 192.168.1.1).

c) Port

:8080

The port number the server is listening on. Each protocol has a default:

  • http → default 80
  • https → default 443
Note: if the port isn't specified, the browser automatically uses the protocol's default. This is why running a Node.js server on localhost:3000 requires the port to be written explicitly — 3000 isn't one of the default ports.

3. Path

/products/laptop

The path to the resource inside the server — similar to a file path on an operating system. It tells you exactly where the resource lives within the server.

4. Query String (Parameters)

?category=electronics&sort=price

Extra data sent to the server as key-value pairs.

  • Starts with ?
  • Each parameter is separated by &
  • Each parameter has the shape key=value

Common uses: filtering, search, sorting, pagination (e.g., ?page=2&limit=10).

5. Fragment (Hash / Anchor)

#reviews

Points to a specific section within the same page — it is never sent to the server at all; it's handled entirely on the client side (in the browser).

Practical example: clicking a "Table of Contents" link in an article that jumps to a specific section on the same page uses a fragment.

Section Four

URL vs. URI — The Real Difference

One of the most commonly confused topics — here's the logical breakdown.

URI = Uniform Resource Identifier

"Identifier" means anything that establishes the identity of a resource, whether through its location or its name — without necessarily saying exactly where it is.

URI Splits Into Two Types

1. URL (Locator) — specifies "where" the resource is and how to reach it

https://example.com/image.png

This is a URL and a URI at the same time, because it identifies the resource through its location.

2. URN (Uniform Resource Name) — specifies the resource's "name" without saying where it is

urn:isbn:0451450523

This is a URN — it tells you "this book's identifier/name is such-and-such" but doesn't tell you where to find it. Like a book's barcode number — it identifies which book it is, without pointing you to its location.

The Relationship Between Them

URI (the general identifier)
 ├── URL (specifies location + how to access it)
 └── URN (specifies name only)

Every URL is a URI, but not every URI is a URL.

Why These Names Exist

  • Identifier (URI): the broad umbrella term — "anything that establishes a resource's identity"
  • Locator (URL): a subtype of URI focused on "location + access" (like a GPS location)
  • Name (URN): a subtype of URI focused on a "permanent name/identity," regardless of location (like a national ID number)

Practical, Real-World Usage

In day-to-day MERN development, you'll use URL almost exclusively (API links, pages, images, etc.). URN is rare in ordinary applications — it shows up more in formal classification systems like ISBNs for books, or in some XML Namespace specifications.

Interview note: in everyday usage, people say "URL" and "URI" as if they're the same thing, and modern browsers and specifications (like the WHATWG URL Standard) largely treat them as near-synonyms in practice. But if asked in an interview for the precise technical distinction, the explanation above is the correct answer.

Section Five

Tips & Tricks

1. URL Encoding (Very Important)

Not every character is allowed as-is in a URL. A space, for example, gets converted to %20 or +.

"laptop bag" → laptop%20bag

In Node.js/JavaScript:

encodeURIComponent("laptop bag & more")
// Result: "laptop%20bag%20%26%20more"
Tip
  • Use encodeURIComponent() on any value you place in a query string that you're not certain is safe (e.g., user input), to avoid characters like & or # breaking the URL's structure.

2. Path Parameters vs. Query Parameters (Common Interview Question)

/users/123          ← Path Parameter (core part of the resource's identity)
/users?id=123        ← Query Parameter (a filter/extra data)

Rule of thumb: if the data is a core, essential part of the resource's identity (like a user's ID), use a path parameter. If it's optional or used for filtering, use a query parameter.

3. The Trailing Slash Sometimes Matters

/products
/products/

On some servers (and certain Express.js configurations), these can be treated as two different routes. Stay consistent across your project.

4. URLs Have a Maximum Length

Most browsers and servers enforce a maximum URL length (typically around 2000 characters). If you need to send a large amount of data, use a POST body instead of stuffing it into the query string.

5. Case Sensitivity

  • The Scheme and Host are not case-sensitive (HTTP://EXAMPLE.COM = http://example.com).
  • But the Path can be case-sensitive depending on server configuration (/Products may differ from /products).

Section Six

Common Interview Questions

Foundational Questions

Q1: What are the parts of a URL?

Scheme, Host, Port, Path, Query, Fragment — as broken down in Section Two.

Q2: What's the difference between a URL and a URI?

URI is the broad, umbrella term; URL is a subtype of it that specifically identifies location.

Q3: What's the difference between a Path Parameter and a Query Parameter, and when do you use each?

See the rule of thumb in the Tips section — core identity data goes in the path, optional/filter data goes in the query string.

Deeper Questions

Q4: What happens when you type a URL into a browser and press Enter?

A classic, comprehensive question. You're expected to walk through: (1) the browser parses the URL, (2) a DNS lookup resolves the domain to an IP address, (3) a TCP connection is established with the server, (4) if HTTPS, a TLS handshake occurs, (5) an HTTP request is sent, (6) an HTTP response is received, (7) the browser renders the HTML and begins fetching additional resources (CSS, JS, images).

Q5: What is DNS and what role does it play in a URL?

DNS translates a domain name (e.g., google.com) into an actual IP address, since servers communicate via IP addresses, not names.

Q6: Why use HTTPS instead of HTTP?

For encryption — data between the browser and server stays encrypted, so no one can eavesdrop on it in transit (protection against man-in-the-middle attacks).

Q7: What is a Query String and how do you access it in Express.js/Node.js?

app.get("/products", (req, res) => {
  console.log(req.query);  // { category: 'electronics', sort: 'price' }
});

Q8: What's the difference between an Absolute URL and a Relative URL?

Absolute: https://example.com/products/laptop
Relative: /products/laptop

A relative URL depends on the current base URL (i.e., whatever page you're currently on).

Q9: What is URL Encoding and why do we need it?

Because certain characters (space, &, #, ?) have special meaning within the URL's own structure — using them unencoded as a plain value would break the URL's structure or be misinterpreted.

A Possible Trick Question

Q10: Does the Fragment (#) get sent to the server?

No, never. The fragment is read and handled entirely on the client side (in the browser) and never reaches the server. This is used by Single Page Applications (like React Router, historically) to change the "displayed view" without triggering a new request to the server.
