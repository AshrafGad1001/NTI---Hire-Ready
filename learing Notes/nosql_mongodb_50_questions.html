Part One

SQL vs. NoSQL, ACID vs. BASE, CAP Theorem

Question 1

What is the core difference between SQL and NoSQL databases?

SQL databases are relational, structured, use fixed schemas with tables and Foreign Keys, are ACID-compliant, and scale vertically. NoSQL databases are non-relational, use flexible schemas (documents, key-value pairs, wide columns, or graphs), follow the BASE model instead of strict ACID, and scale horizontally through sharding. SQL suits complex, stable relationships and financial-grade accuracy; NoSQL suits variable-shaped data, rapid development, and massive scale.

Question 2

When would you choose SQL over NoSQL, and vice versa?

Choose SQL when data has complex, stable relationships requiring strong consistency (e.g., banking transactions) or when reports need many joins. Choose NoSQL when the data shape varies frequently, development speed matters, or the system must scale to millions of users with flexible, evolving schemas.

Question 3

Explain what each letter in ACID stands for.

Atomicity: a transaction completes fully or not at all. Consistency: data moves from one valid state to another without violating rules. Isolation: concurrent transactions don't interfere with each other. Durability: once committed, data survives even a crash.

Question 4

Explain what each letter in BASE stands for.

Basically Available: the system always responds, even if degraded. Soft state: data can change over time even without new input, due to replication catching up. Eventually consistent: replicas aren't instantly identical but converge over a short time.

Question 5

Give a real-world example of when ACID matters and when BASE is acceptable.

ACID matters for a bank transfer — a partial transfer where money leaves one account but never reaches another is unacceptable. BASE is acceptable for something like a "Like" counter on a social media post, where a short delay before all viewers see the updated count causes no real harm.

Question 6

Does MongoDB support ACID transactions? Explain.

Yes — since MongoDB 4.0, multi-document ACID transactions are supported on replica sets (and from 4.2 on sharded clusters). This means MongoDB isn't purely BASE; it lets developers choose ACID guarantees when accuracy across multiple documents/collections is essential, while relying on document-level atomicity and eventual consistency elsewhere for speed.

Question 7

What is the CAP Theorem, and why can't a distributed system guarantee all three properties at once?

CAP states that a distributed database can guarantee at most two of: Consistency (every node returns the same data), Availability (every request gets a response), and Partition Tolerance (the system keeps working despite network failures). Since network partitions are inevitable in distributed systems, Partition Tolerance isn't really optional — so the real trade-off during a partition is between Consistency and Availability.

Question 8

Is MongoDB CP or AP by default? How can this be tuned?

MongoDB defaults to CP — it prefers to pause writes on the primary rather than risk returning inconsistent data across replicas. This can be tuned via Read Concern (e.g., readConcern: "majority") and Write Concern (e.g., writeConcern: { w: "majority" }), trading some speed for stronger consistency guarantees, or vice versa.

Part Two

NoSQL Types & BSON

Question 9

What are the four main types of NoSQL databases? Give an example of each.

Key-Value Store (Redis, Riak) — simplest form, ideal for caching and sessions. Wide Column Store (Cassandra, HBase) — column-oriented, ideal for time-series and massive write volume. Document Store (MongoDB, CouchDB) — flexible JSON/BSON documents, the most common type in MERN apps. Graph Store (Neo4j, InfiniteGraph) — nodes and edges, ideal for relationship-heavy data like social networks or fraud detection.

Question 10

Why is Redis often used alongside MongoDB in the same application?

Redis is a key-value store optimized for extremely fast lookups, making it ideal for caching frequently accessed data, storing sessions, or rate-limiting — tasks MongoDB can technically do but not as fast for simple key-based access patterns. They complement each other: MongoDB handles rich, structured application data, while Redis handles ephemeral, high-speed lookups.

Question 11

What is BSON, and why does MongoDB use it instead of plain JSON?

BSON (Binary JSON) is the binary format MongoDB actually stores documents in. It's used instead of plain JSON because it supports precise data types (Int32, Int64, Double, Decimal128), a native Date type, native Binary Data, faster traversal (field lengths are known upfront), and a native ObjectId type — none of which plain JSON provides on its own.

Question 12

What is the maximum size of a single MongoDB document, and why does that limit exist?

16MB. This limit exists because BSON uses an Int32 to store document size, capping the maximum representable size at 16MB. This is a key reason unbounded arrays (like a huge, ever-growing list of comments) should use referencing instead of embedding.

Question 13

If the JSON you see in a Postman response isn't how MongoDB stores the data, what's actually happening?

MongoDB stores data as BSON on disk (inside WiredTiger storage engine files). The JSON shown in a client response is a textual representation automatically converted from the underlying BSON — it's a display/transport format, not the storage format.

Question 14

Name two data types BSON supports that plain JSON does not.

Any two of: a native Date type, a native ObjectId type, precise numeric types (Int32, Int64, Decimal128), and native Binary Data for storing raw binary content directly.

Part Three

Embedding, Referencing & Design Patterns

Question 15

What is the "Embedding" pattern, and when should you use it?

Embedding stores related data directly inside the parent document. Use it when the relationship is one-to-few, the related data is almost always read together with the parent, and it doesn't change frequently or independently. It gives fast single-query reads and atomic updates, but risks document bloat and duplication if misused.

Question 16

What is the "Referencing" pattern, and when should you use it?

Referencing stores just an ID pointing to another document, similar to a Foreign Key. Use it for large one-to-many or many-to-many relationships, data that changes frequently and independently, data shared across multiple parents, or arrays that could grow unbounded. It keeps documents small but requires a $lookup at read time.

Question 17

Describe the Subset Pattern and give a practical use case.

The Subset Pattern stores only a small, relevant portion of related data (e.g., the latest 5 reviews) directly on the parent document, while the full dataset lives in a separate collection. A practical use case: showing the "latest 3 reviews" on a product page instantly, without running an aggregation query on every page load.

Question 18

Describe the Bucket Pattern and give a practical use case.

The Bucket Pattern groups a batch of readings/events from the same time window into a single document, instead of creating one document per individual event. It's commonly used for time-series data, such as grouping a sensor's per-minute temperature readings into one document per hour, drastically reducing the total document count and index size.

Question 19

Describe the Computed Pattern and give a practical use case.

The Computed Pattern pre-calculates a value that's read frequently but changes rarely, storing it as a ready field instead of recalculating it on every read. A practical use case: storing averageRating directly on a Product document, updated only when a review is added or removed, instead of running an aggregation across all reviews every time the product page loads.

Question 20

What's the most dangerous common mistake beginners make with the Embedding pattern?

Over-embedding data that is mutable and shared across many documents — for example, embedding a full copy of product details (name, price, stock) inside every order. If the product's price changes later, every past order containing that product would need updating, which is a disaster. The fix is to embed a point-in-time snapshot (e.g., the price at the moment of purchase) rather than a live copy expected to stay in sync.

Question 21

What are unbounded arrays, and why are they a common schema design mistake?

An unbounded array is one that can grow without any practical limit — for example, embedding every review directly inside a product document. This risks hitting the 16MB document size limit and causes performance to degrade well before that, since the document becomes slower to read and write as it grows. The fix is to use referencing or the Subset Pattern instead.

Question 22

What is the "golden rule" that should guide every embed-vs-reference decision?

"Data that is accessed together should be stored together." The decision should be driven by actual access patterns (the queries your application really runs), not by an abstract sense of relational correctness borrowed from SQL thinking.

Part Four

Mongo Shell, Query Operators & Projection

Question 23

What's the difference between find() and findOne()?

find() returns a cursor pointing to every matching document (could be zero, one, or millions), while findOne() returns only the first matching document directly as an object, or null if nothing matches. Use find() for lists/pagination and findOne() to check existence or fetch by a unique field.

Question 24

What does Projection do, and what's the rule about mixing inclusion and exclusion?

Projection (the second parameter of find()) controls which fields are returned. Setting a field to 1 includes it (all unlisted fields are excluded); setting it to 0 excludes it (all others are returned). You cannot mix inclusion and exclusion in the same projection, except for _id, which can always be explicitly excluded even inside an inclusion projection.

Question 25

Write a query using $and and explain when you'd need it explicitly versus writing conditions directly on one field.

db.posts.find({ $and: [{ likes: { $gt: 200 } }, { likes: { $lt: 500 } }] })
// Equivalent when both conditions are on the same field:
db.posts.find({ likes: { $gt: 200, $lt: 500 } })

Explicit $and is required when combining conditions across different fields, or when the same field needs multiple separate operator objects that can't be merged into one. On a single field with compatible operators, the shorthand form is preferred for readability.

Question 26

What's the difference between $in and $all when querying an array field?

$in matches documents where the field's value matches any one of the given values (or, for an array field, if the array contains at least one of them). $all requires the array to contain every value listed, not just one.

Question 27

Write a query using $elemMatch and explain why it's needed instead of simple dot notation.

db.orders.find({ items: { $elemMatch: { productId: id, quantity: { $gte: 2 } } } })

$elemMatch ensures that multiple conditions are satisfied by the same array element. Without it, MongoDB could match a document where one array element satisfies the first condition and a different element satisfies the second — $elemMatch guarantees both conditions apply to one single element.

Question 28

Explain the correct order for chaining sort(), skip(), and limit() in pagination, and why order matters.

db.products.find()
  .sort({ createdAt: -1 })
  .skip((page - 1) * limitPerPage)
  .limit(limitPerPage);

Sort should come first to establish a consistent order, then skip, then limit. If the data isn't sorted deterministically before paginating, results across pages can duplicate or skip items inconsistently, since the underlying document order isn't guaranteed otherwise.

Question 29

What does the Mongoose "strict" schema option do, and why should it usually stay true?

When strict: true (the default), any field on an incoming document that isn't defined in the schema is silently ignored and not saved. Setting it to false allows arbitrary undeclared fields to be saved, which removes one of the schema's most valuable protections — guarding against unexpected or malformed data.

Question 30

What is the difference between a Mongoose Virtual and a regular schema field?

A regular field is stored in the database. A virtual is a computed property that exists only in the application layer and is never persisted — it's calculated on demand (e.g., priceAfterDiscount). To have virtuals appear in JSON responses, you must enable toJSON: { virtuals: true } in the schema options.

Question 31

What's the difference between Mongoose Instance Methods and Static Methods?

Instance methods (schema.methods.x) operate on a single document and are called on a fetched document instance (e.g., product.isInStock()). Static methods (schema.statics.x) operate on the Model itself and are called directly on the model (e.g., Product.findByCategory(id)), typically used for reusable custom queries.

Part Five

Aggregation Pipeline

Question 32

How does the Aggregation Pipeline fundamentally differ from a single SQL query in terms of execution order?

In SQL, the written syntax follows a fixed logical clause order, and the query optimizer may reorder internal execution for performance without changing the meaning. In an Aggregation Pipeline, stages execute in exactly the order they're written — reordering stages changes the actual result, not just performance.

Question 33

Match each aggregation stage to its closest SQL equivalent: $match, $group, $sort, $project, $lookup.

Question 34

Why should $match generally be placed as early as possible in a pipeline?

Placing $match early filters out irrelevant documents before they reach later, heavier stages — reducing the volume of data each subsequent stage must process, and allowing MongoDB to use available indexes on the filtered field for faster execution.

Question 35

What does $unwind do, and why is it necessary before grouping on array elements?

db.users.aggregate([
  { $unwind: "$skills" },
  { $group: { _id: "$skills", count: { $sum: 1 } } }
])

$unwind flattens an array field into separate documents, one per array element, duplicating the rest of the parent document's fields for each. It's necessary before grouping by individual array values, because $group operates on document-level fields, not on elements nested inside an array.

Question 36

What does $facet allow you to do that a single $group stage cannot?

$facet runs multiple independent sub-pipelines against the same input set in a single aggregation call, returning all their results together as separate named fields. This is useful for building a dashboard with several unrelated statistics (e.g., counts by role, employment stats, and top city) in one query instead of three separate ones.

Question 37

What's the difference between $out and $merge?

$out completely replaces the target collection with the pipeline's output. $merge is more flexible — it can merge results into an existing collection (updating matching documents, inserting new ones, or various other merge strategies) rather than wiping it out entirely.

Question 38

In a $group stage computing an average, what's the difference between using $avg directly versus using the Computed Pattern discussed earlier?

Using $avg in an aggregation recalculates the average from scratch every time the query runs, which can be expensive on large datasets and frequent reads. The Computed Pattern instead pre-calculates and stores that average as a static field on the parent document, updating it only when the underlying data changes — trading a bit of write complexity for much faster reads.

Part Six

Indexing

Question 39

What is a Compound Index, and when is it preferable over two separate single-field indexes?

db.products.createIndex({ category: 1, price: -1 })

A compound index is built from more than one field together. It's preferable when queries commonly filter and sort using multiple fields at once (e.g., filter by category, sort by price) — a single compound index serves that query far more efficiently than two separate indexes would.

Question 40

What's the difference between a Sparse Index and a Partial Index?

A sparse index simply skips documents where the indexed field doesn't exist at all. A partial index is more flexible — it lets you define an arbitrary filter expression, so the index only covers documents matching that specific condition (e.g., only "completed" orders), regardless of whether the indexed field itself is present or absent.

Question 41

List three benefits and three drawbacks of adding indexes to a collection.

Benefits: faster reads (avoids full collection scans), faster sorting when an index matches the sort field, and the ability to enforce uniqueness. Drawbacks: slower writes (every index must be updated on insert/update/delete), extra disk and RAM usage, and a hard cap of 64 indexes per collection.

Question 42

How do you check whether a query is actually using an index, and what output indicates it isn't?

db.users.find({ role: "trainee" }).explain("executionStats")

Run .explain("executionStats") on the query. If the result shows "stage": "IXSCAN", an index was used. If it shows "stage": "COLLSCAN", MongoDB performed a full collection scan instead, meaning no suitable index was used.

Question 43

Why shouldn't you index a field like "viewsCount" that updates on almost every read of a document?

Every write must update every index on the affected fields. A field that changes extremely frequently would force constant index maintenance on every update, adding significant write overhead for little to no read-performance benefit, since that field is rarely used as a filter or sort criterion in the first place.

Schema Design Process & Relationship Types

Question 44

List the six steps of the NoSQL Schema Design Process in order.

1) Identify the entities. 2) Identify the most common queries (access patterns) — the most important step. 3) Identify the relationships between entities. 4) Apply the right pattern (embed/reference/subset/bucket/computed) to each relationship. 5) Review the design against common mistakes (unbounded arrays, deep nesting, over-embedding mutable shared data). 6) Audit a real project's existing schemas against actual access patterns.

Question 46

What three questions should you ask for every relationship before choosing embed vs. reference?

1) Growth rate — is the count small and stable, or large and increasing? 2) Update frequency — does the data change often or rarely? 3) Read-together frequency — is the child data needed every time the parent is fetched?

Part Eight

Schema Validation & Transactions

Question 47

What is the purpose of $jsonSchema validation in MongoDB, and does it replace application-level validation (e.g., Mongoose)?

$jsonSchema enforces structural rules (required fields, types, ranges, enums) at the database engine level, rejecting non-compliant writes regardless of which client or script performs them. It does not replace application-level validation — the two work together: Mongoose gives fast, user-friendly feedback in the app; database-level validation is the last line of defense protecting data integrity even if the application is bypassed.

Question 48

What's the difference between validationLevel: "strict" vs. "moderate", and when would you use "moderate"?

"strict" (the default) applies the validation rule to all inserts and updates, even on pre-existing documents that don't already comply. "moderate" applies the rule to new inserts but allows updates to non-compliant legacy documents as long as the update doesn't make them worse. Use "moderate" when retrofitting validation onto a collection that already contains data not yet conforming to the new rule, to avoid breaking existing writes.

Question 49

Why are multi-document transactions needed in MongoDB even though a single document write is already atomic?

A single document's write is guaranteed atomic on its own, but many real operations (e.g., a purchase) need to update multiple documents across multiple collections together — decrementing stock, creating an order, and deducting a user's balance. Without a transaction, a crash partway through could leave the system in an inconsistent state (e.g., stock decremented but no order created). A transaction guarantees all these operations succeed together or are all rolled back.

Question 50

What are the infrastructure requirements for running transactions in MongoDB, and what happens on a TransientTransactionError?

Transactions require MongoDB to run as a Replica Set (even a single-node one for local development) or a Sharded Cluster — they are not supported on a standalone instance. Supported since MongoDB 4.0 for replica sets and 4.2 for sharded clusters. A TransientTransactionError indicates a temporary conflict (e.g., another transaction modifying the same document), and the recommended practice is to retry the transaction rather than treat it as a permanent failure.
